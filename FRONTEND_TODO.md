# Фронтенд CUTPOINT — план доводки

Два полных круга: идеи → реализация → аудиты. Затем повтор. Решения принимаются на месте,
без остановок и вопросов. Одновременно работает не более трёх агентов, и только с непересекающимися зонами файлов.

## Что уже есть

Лендинг на React 19 + TypeScript + Vite, отдаётся Python-сервером (`uv run neftecode serve`).
Восемь этапов пайплайна + экран условий, каждый на своей пастельной подложке во всю ширину окна.
Живой SSE-поток: данные приходят по мере расчёта, работа агентов видна по событиям.
Левая панель появляется после запуска, держится по центру окна.
Визуальная система — `DESIGN.md` (монохром + восемь подложек + янтарь логотипа).

## Жёсткие ограничения (нарушать нельзя ни на одном шаге)

1. **Честность интерфейса выше красоты.** Бейджи происхождения чисел, «Живая модель не
   участвовала», «данных не передавали, а не что всё в порядке», «Результат сценарный»,
   предупреждения об отсутствии срезов — ни одна оговорка не удаляется ради вида.
   Пустой блок пишет, что данных нет, а не выглядит заполненным.
2. **Рисовать только то, что есть в payload.** Не выдумывать числа, не имитировать данные.
3. Ноль комментариев в коде. TypeScript, именованные экспорты, файлы ≤250 строк.
4. Никаких новых npm-зависимостей и внешних запросов в рантайме (закрытая сеть).
5. Движение: 150–600 мс, без спиннеров, параллакса, пружин, отскоков.
   Обязательный `@media (prefers-reduced-motion: reduce)`.
6. Контраст не ниже WCAG AA на всех восьми подложках, считать цифрами.
7. Не вешать `overflow: hidden`, `isolation`, `contain`, `transform`, `filter` на `.stage`,
   `.stages` и их предков — это трижды ломало цветные подложки.
8. Порт 8765 занят сервером пользователя. Работать на своём, пересобирать `npm run build`
   после каждой заметной правки.
9. Git не трогать. Python в `src/neftecode/` — только если без этого никак.
10. **Никакого ИИ-слопа.** Это здравый, взрослый продукт для оператора НПЗ, а не витрина
   генеративных эффектов. Запрещены: градиентные заливки ради красоты, свечения, glassmorphism,
   эмодзи в интерфейсе, декоративные частицы, фальшивые «терминальные» логи, печатающийся текст,
   пульсирующие ореолы, «нейронные сети» из точек и линий, бессмысленные счётчики и прогресс-бары
   без реального смысла, пафосные формулировки в копирайте. Каждый элемент отвечает на вопрос
   оператора; если не отвечает — его не должно быть. Анимация объясняет изменение состояния,
   а не развлекает.

# КРУГ ПЕРВЫЙ

## Ф1. Три аудита идей (строго по очереди, один агент за раз, только идеи, код не трогают)

Каждый изучает проект и возвращает список предложений с обоснованием и оценкой стоимости.
Ничего не реализуют.

### Ф1.1 — Визуализация данных
Что из payload можно показать графически, а сейчас лежит текстом или таблицей.
Траектории, распределения, сравнения планов, отсев кандидатов по раундам, запасы по качеству,
устойчивость к отклонениям, чувствительность к оценке резервуара.

### Ф1.2 — Визуализация работы агентов
**Главный по важности.** Как показать мультиагентность так, чтобы жюри увидело работу,
а не список строк. Диалог оркестратора со специалистами, выбор инструментов, сужение поиска
ограничением, вердикты с уверенностью, различие живой модели и детерминированной политики.

### Ф1.3 — Движение, микровзаимодействия, подача
Что оживить, где добавить обратную связь, как подать переход между этапами, как показать
ход расчёта. Плюс общая художественная оценка: чего не хватает, что выглядит шаблонно.

## Серверная находка — живой прогон зависал (починено)

При проверке выяснилось, что живой прогон на 8765 доходил до gate за 687 мс и дальше вис бесконечно:
ни событий агентов, ни `screen`. Фронтенд был ни при чём.

Причина: модель по умолчанию `glm-5.3-flash` (`ZAI_DEFAULT_MODEL` в `config.py`) — reasoning-модель.
Замерено на одинаковом запросе с вызовом инструмента:

- `glm-5.3-flash` — 160 с на один вызов
- `glm-4.6` — 19 с на тот же вызов

При лимите 12 вызовов это ~32 минуты против ~4. При этом `AGENT_TIMEOUT_SECONDS` = 600 с,
то есть прогон не падал с ошибкой, а молча висел.

**Что сделано.**

1. В `.env` (gitignored, ключ в репо не попадает) добавлено `ZAI_MODEL=glm-4.6`. Код не тронут:
   `ZAI_MODEL` уже читался из окружения. Резервная копия — `.env.bak`.
2. Починено вводящее в заблуждение сообщение валидатора в `tool_registry.py`. Строка длиннее
   `maxLength` давала ошибку «ожидается строка», хотя строка была передана — модель не могла
   сама себя исправить и в живом прогоне потеряла два вызова на `ask_quality_agent` и
   `ask_reliability_agent`. Теперь сообщение называет предел и требует сократить.

**Проверено после правки** (свой порт 8791, пользовательский 8765 не тронут): полный прогон доходит
до конца за 231 с, 36 событий агентов, `screen` и `end` приходят. Тесты:
`tests/architecture/test_layers.py` — 8 passed; `test_session_tools`, `test_loop`,
`test_agent_contracts` — 86 passed.

**Что из этого следует для фронтенда.** Живой прогон с моделью длится минутами, а не секундами.
Значит очередь раскрытия с выдержкой 260 мс ничего не тормозит (события и так редкие),
а вот долгое ожидание между событиями агентов (до 44 с на один вызов) должно быть
честно показано: оператор видит, что система ждёт модель, а не зависла.
Карточка консультации из волны 3 должна уметь показывать `decision: "error"` с `reason_codes`.

## Итоги аудита движения — к исправлению

Общая оценка: движение в хорошей форме. Ни одной бесконечной анимации, ни одного
спиннера, ни одного `transition: all`, одна кривая `--ease` везде.

### Дви-1 (важное, честность). `useCountUp` всегда стартует с нуля

Кадр считается как `target * eased`. Для «Планов рассмотрено: 0 → 128» это честно:
перебор шёл от нуля. Для остального — нет:

- Концентрация серы никогда не была нулём — отсчёт изображает несуществовавший процесс.
- «Запас до предела» бывает отрицательным: отсчёт от нуля вниз проезжает через «запас есть»
  к «запаса нет» — противоположный смысл в первые полсекунды.
- Стоимость тонны с четырьмя дробными разрядами — 520 мс нечитаемого мельтешения.
- Индекс тяжести и дельты (изменений уставок) не имеют шкалы от нуля.

Правило: **`count` допустим только на целочисленных количествах, которые сервер набирал
перебором.** Всё с единицей измерения (мг/кг, т, у.е./т) или являющееся индексом/дельтой — без `count`.

### Дви-2. Счётчики играют после окончания расчёта

Запуск на монтировании, а монтирование происходит, когда payload уже целиком пришёл.
Числа «набегают» после того, как расчёт закончился.

### Дви-3. Ожидание подано четырьмя поверхностями

Честность высокая, понятность средняя. Самая ценная строка — «ждём ответа модели, N с» —
спрятана в этапе 6, куда надо доскроллить. Поднять факт ожидания в закреплённую шапку.
Блок `.waiting` одет в пунктир, а пунктир в этой системе означает «нет данных» — а ожидание
это нормальный ход работы. Переодеть в сплошную рамку, без добавления движения.

### Дви-4. Семь keyframes там, где нужно два

`line-in`, `act-in`, `trace-in` — байт в байт одно и то же; `live-appear` — то же, но 4px
вместо 6px; `stage-in`, `plate-in`, `action-in` — три одинаковых fade.
Свести к `enter-up` и `enter-fade`.

### Дви-5. График собирается 840 мс

`chart-draw` 600 мс плюс точки с задержкой 540 мс. Ужать до ~500 мс.

### Дви-6. Хардкод 200ms вместо токена

В `motion.css`, `rail.css`, `strip.css`. Заменить на `var(--motion-panel)`.

### НЕ трогать

`scale(0.98)` за 80 мс на нажатии кнопки (обратная связь обязана быть быстрее порога
восприятия); `revealQueue.ts`; `autoscroll.ts` и проверки matchMedia в `useRun.ts` и `Rail.tsx`
(CSS `scroll-behavior` не действует на JS-аргумент `scrollIntoView`, это не дублирование);
мгновенный скролл при прыжке дальше трёх этапов; глобальный блок reduced-motion
в `base.css`; защитные `overflow: visible; isolation: auto; contain: none` у `.stages`;
отсутствие анимации у ячеек бюджета и уверенности.

## Итоги аудита интерфейса — к исправлению

Прогон проверен вживую на полном payload: 129 проверок Gate, 265 чисел, 16287 px прокрутки.

### Инт-1 (главное). Интерфейс врёт про единицы

`DecisionStage` показывает `₽/т`, тогда как бэкенд объявляет величину как `у.е./т` и прямо
оговаривает «условные единицы сценария, не тарифы завода». Соседний `ChoiceStage`
пишет честно. Нарушение п.1 в самой заметной точке продукта.

### Инт-2. Два провала контраста от `opacity`

- `.stage--pending { opacity: 0.55 }` гасит этап целиком: `--muted` падает до **2.25–2.41**
  при пороге 4.5, текст в белой карточке до **3.49–3.65**. Провал на всех восьми подложках.
- `.rail__item--pending .rail__order { opacity: .55 }` даёт **2.55**. Вес 400 не даёт права
  на порог крупного текста.

Всё остальное проходит AA с запасом: 26 проверенных классов, минимум 5.30.

### Инт-3. Рейка показывает не тот этап

`rootMargin` даёт полосу наблюдения 144 px при окне 720. Этапы высотой 1000–2940 px
полностью перекрывают полосу и не порождают нового `isIntersecting`. Замерено:
`#decision` занимал всё окно, а рейка и `aria-current` показывали «4 Кандидаты».

### Инт-4. Офлайн оставляет клавиатуру без цели

При недоступном `/api/options` замерено **0 фокусируемых элементов**. Кнопки повтора нет.
Плюс два сообщения об одном факте, второе протекает деталью `Error:`.

### Инт-5. Живые области не объявлены

`aria-live` не встречается в коде ни разу. Восемь секций приходят асинхронно минутами.

### Инт-6. Таблица молча режет список

`.slice(0, 25)` в `GateStage` на таблице «что не прошло» без пометы.

### Инт-7. Смысл цветом в одиночку

`.live__cell--pass/fail/unknown` различаются только цветом левой границы —
единственное такое место в проекте.

### Инт-8. Мелкое

- `.matrix__label` и `.matrix__axis` — 10 px на содержательных подписях.
- `.masthead__verdict` 28 px перебивает `h2` этапа (24 px); до запуска самый крупный
  текст экрана — «прогона ещё не было».
- `skip` в `useRun` реализован, но нигде не подключён.
- Токены `--band-hover-*` заведены и не используются ни одним правилом.
- 30 бейджей происхождения конкурируют по весу со значениями (убирать нельзя по п.1,
  но вес снизить можно).

### Что подтверждено как хорошее

П.7 соблюдён полностью. П.10 соблюдён полностью: ни одного `linear-gradient`,
`box-shadow`, `backdrop-filter`, `blur`, `text-shadow` во всех CSS; ни одной `infinite`-анимации.
Матрица Gate названа образцовой работой. Тексты `Empty` и `Note`, `BudgetMeter`

## Итоги аудита полировки

Три находки проверены лично по коду и подтверждены.

### Пол-1 (блокирующее). Прогон нельзя остановить

Кнопка сброса рендерится только при `status !== "idle" && !running`. Во время прогона
(231 с, паузы до 44 с) единственная кнопка — задизейбленная «Идёт расчёт…».
`stop()` реализован и умеет `abort()`, но до него нет дороги из интерфейса.

### Пол-2 (блокирующее). Обрыв потока выглядит как успех

Цикл чтения выходит по `chunk.done` без проверки, пришёл ли `screen`. При обрыве сети
исключения нет, `.catch` не срабатывает, состояние навсегда остаётся `running`.
Страница вечно показывает «идёт» и «поток продолжается».

### Пол-3. Оговорка честности мертва

`stageSource` объявлен, инициализирован пустым и читается — но не записывается нигде
(проверено grep: только объявление и чтение). Текст «это не длительность расчёта
этапа» не показывается ни разу. Оператор видит время этапа без предупреждения.

### Пол-4. Хардкод лимитов бюджета выдаётся за данные

Колонка происхождения помечает только числитель, а выдуманный знаменатель идёт как факт.

### Пол-5. Смена сценария стирает выбор оператора

`fault` жёстко сбрасывается в `healthy`. Оператор запустит не тот прогон без предупреждения.

### Пол-6. Согласованность терминов и оформления

- `throughput_tph` назван пятью разными способами; «Выпуск» в т и «Выпуск» в т/ч различаются
  только единицей.
- Две функции `seconds()` в разных файлах дают «1,4 с» и «1.4 с» на одном экране.
- Лампа этапа считается дважды (рейка и сам этап) по разным формулам — могут разойтись.
- «Данных нет» подаётся пятью разными оформлениями.

### Пол-7. Печать не предусмотрена вовсе

Ни одного `@media print`. DESIGN.md прямо обещает работу на чёрно-белой печати —
обещание ничем не подкреплено: фиксированная рейка, обрезанные панели и таблицы.

### Пол-8. Контраст `--mercury` ниже порога

`#8b8b8b` даёт 2.96:1 на vellum и 2.17:1 на цветной подложке. Используется на текстовом
символе в JSON и на смыслонесущей лампе состояния.

### Пол-9 (шаблон). Цветной боковой кант в шести файлах

Один и тот же левый кант навешен на шесть разных сущностей, в каждом файле своя
толщина (1/2/3px). Система DESIGN.md строит различия на начертании рамки целиком —
боковой кант из этой логики выпадает.

## Итоги Ф4 — что нашли аудиты идей

Три аудита по направлениям данные / агенты / подача. Ключевые находки проверены лично.

### Недоделки, а не идеи: сервер шлёт, фронт теряет

- `llm_choice_overridden` — флаг «оркестратор назвал один план, детерминированный код
  выбрал другой». Самый сильный аргумент «модель не главная» — не читается вообще.
- `vetoed_candidates` — карта вето. В плане была ошибочно помечена сделанной.
- `provider_label` — объявлен в типе, не читается ни одним компонентом.
- `budget.consults`, `replans`, `robustness_runs` — три счётчика с настоящими знаменателями.
- `finish_reason` у вызовов модели; `step` в событиях (видно, что специалист делал 3 итерации).
- `alternatives[].controls` и `.recipe` — приходят и выбрасываются; именно они отвечают
  на вопрос «чем этот план отличался».

### Нарушение п.2 в самом заметном графике

`Trajectory` соединяет дискретные точки прямыми, то есть утверждает промежуточные
значения, которых никто не считал. Усугубляется тем, что в statements есть
запаздывание отклика 2 ч — сера между точками не обязана идти по прямой.
Плюс плоская линия вырожденного случая не подписана, хотя соседние компоненты
вырожденность называют словами.

### Прочее из аудитов

- `MarginBars` молча отбрасывает 10 из 15 statements.
- Запас по уставкам и отгрузке виден только ячейками матрицы.
- `familyOf` не знает трёх семейств — сырые английские идентификаторы вперемежку с русскими.
- `AgeBars` обрезает превышение: «просрочен вдвое» и «ровно на пределе» неразличимы.
- `RobustnessMap` рисует шкалу для неприменённых возмущений.
- Долгие паузы (до 44 с): можно честно сказать, кого ждём и на каком шаге,
  и что уже собрано к этой секунде — без анимации и без процентов.

### Чёрный список пополнился

Sankey потока кандидатов (склеит несопоставимые шкалы планов и проверок),
радарная диаграмма по свойствам (требует нормировки, от которой отказались),
усреднение confidence двух агентов, равномерная ось времени для событий с разрывами
0,2 с и 44 с, минимальная видимая длина для нулевых слагаемых.

### Решение по `useCountUp` — механизм удалён целиком

Счётчик запускался на монтировании, а монтирование происходит, когда payload уже целиком
пришёл. То есть числа набегали **после** конца расчёта, рисуя промежуточные
значения, которых в payload не было — нарушение п.2 и п.10.

Половинчатое состояние (часть счётчиков с анимацией, часть без) хуже любого из двух
вариантов. Проп `count` снят со всех мест, `useCountUp.ts` удалён.
Если появится инкрементальная отдача по SSE — счётчик станет честным и вернётся.
