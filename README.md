# Нефтекод

Советчик оператору связанной цепочки АВТ → гидроочистка → смешение товарного дизельного топлива.
На момент решения система собирает доступные данные, проверяет их пригодность, прогнозирует серу
после гидроочистки, строит короткие планы на ближайшие часы с учётом запаздывания отклика и
остатков компонентов, отбрасывает всё, что нарушает жёсткие ограничения, и выдаёт либо план,
либо сохранение режима, либо мотивированный отказ.

Это исследовательский прототип. Он ничем не управляет и не разрешает выпуск товарного топлива:
`commercial_release_allowed` во всех результатах ложно, потому что проверены не все требуемые
свойства продукта.

## Что здесь реально, а что задано сценарием

| Реально | Задано сценарием |
|---|---|
| Телеметрия АВТ и 24-2000, 189 217 строк с шагом 10 минут | Объёмы резервуаров, резервный и лёгкий компоненты, их свойства (`open`) |
| Лабораторные анализы ЛИМС и поточный анализатор | Цены и условные затраты |
| Причинный прогноз серы `ПАК + медиана 20 последних доступных ЛИМС−ПАК`, проверенный на пяти rolling-полугодиях; фактическое покрытие интервала публикуется | Модель отклика АВТ (тегов печей К-2 нет) и отклик ГО по расходу |
| Проверка доступности и согласованности источников; пороги выведены из истории и применяются во всех контурах | Предел T95 (цетан и плотность — от экспертов, сообщение 582) |
| Уставки ГО на момент решения — измерения `ht.T6`, `ht.F9`; приток резервуара — `ht.F26`·ρ | Запаздывание отклика и политика переключений |
| Отклик серы на температуру входа реактора — β = −0.43 мг/кг/°C по данным, с интервалом и областью применимости | Абсолютная модель цепочки (только для синтетических сцен) |
| Проверка 17 формул виртуальных анализаторов | Сцена «ухудшение сырья» |

Значение ровно 307 — заглушка опроса (эксперты, сообщение 582: «выброс»): при загрузке оно становится пропуском,
колонка `avt.D10` из одних заглушек не используется. Пороги доверия к источникам не заданы руками: при обучении они
выводятся из истории до 2025-01-01 и сохраняются в модели — ЛИМС старше двух суточных интервалов проб (48 ч), ПАК
старше трёх периодов опроса (30 мин), зависание — 4 одинаковых показания подряд (так редко бывает у живого прибора),
конфликт ПАК–ЛИМС — выше 95-го перцентиля расхождения (4.75 мг/кг), телеметрия неполна — от 10 одновременно пропавших
датчиков из 96 (провал между обычным режимом и сбоями опроса). ТЗ требует проверку, но чисел не даёт.
Для `scenes`, `screen` и `serve` это верно, пока рядом лежит `artifacts/source_rules.json` (его пишет `train`,
и он входит в комплект сдачи). Без этого артефакта `infrastructure/config/trust_rules.py` берёт пороги из
`config/experiment.json`, где заданы
только два предела возраста, и три правила молча возвращаются к прежним константам, заданным руками: зависание —
6 одинаковых показаний вместо выведенных 4, конфликт ПАК–ЛИМС — `max(3; 0.5·ЛИМС)` вместо 4.749 мг/кг, неполнота
телеметрии — 0.1 вместо 0.0938. Откуда пришли пороги, подписано на экране оператора: `derived:artifacts/source_rules.json`
или `fallback:config/experiment.json`. Команда `advise` — исключение: она всегда берёт пороги доверия из
загруженного `artifacts/model.pkl`, поэтому отдельный `source_rules.json` на её результат не влияет.

Два требования ТЗ объявлены не выполненными. Приоритет источников качества ЛИМС → ПАК → ВАК реализован только
до ПАК: формулы виртуальных анализаторов проверены (`src/neftecode/evaluation/vak.py`), но ни один их результат
не служит значением для решения (`src/neftecode/infrastructure/data/quality.py`). Порог корреляции 0.5 прошли две
формулы. `24-2000:GODT:IBP` даёт r = 0.539 и MAE 5.646 °C, что хуже постоянной медианы тех же проб
(5.403 °C). `AVT6:350:T50` даёт r = 0.515 и MAE 4.778 °C против 8.229 °C у медианы, но её связь с точкой
ЛИМС АВТ 1 — неподтверждённая гипотеза по положению в процессе, а T50 этой фракции не является ни серой,
ни T95, ни цетановым числом товарного ДТ. Поэтому обе формулы остаются проверочными расчётами, а не источниками
значения для решения; разбор — `context/vak-review.md`. Соотношение ВСГ/сырьё, названное в ТЗ среди
возможных воздействий, не моделируется как управляющая переменная. В данных есть `ht.F2` — «Газовая схема.
Расход на линии от ЦК-201», нм³/ч, и `ht.F25` — расход свежего ВСГ с КЦА; оба ряда заполнены. Однако справочник
не задаёт направление и границы линии F2 и не подтверждает, что весь измеренный поток проходит через Р-202,
поэтому F2 можно считать только кандидатом на показатель циркуляции, а не доказанным расходом газа через реактор.
Отношение F2 к массовому расходу сырья `ht.F9` вычислимо, но для него не заданы безопасный диапазон управления
и идентифицированный отклик качества. До такого подтверждения воздействие в оптимизатор не добавляется.

Данных по смешению завод не выдавал; синтетический сценарий разрешён экспертом. Каждая
величина в сценарии несёт единицу и происхождение (`given` / `derived` / `scenario` / `open`),
поэтому сценарную константу нельзя прочитать как измерение.

## Запуск

Нужны Python 3.12 и [`uv`](https://docs.astral.sh/uv/). Все команды — из корня репозитория.

```sh
uv sync --frozen
uv run pytest -q
```

Первый запуск скачивает зависимости; дальше всё считается локально. Для тестов и
детерминированного контура внешние API и ключи не нужны (набор тестов отключает LLM-агентов),
`uv.lock` фиксирует версии. В рабочем каталоге с `task/` и `artifacts/model.pkl` ожидается
**1208 passed, 0 failed, 0 skipped**. В чистой копии, собранной `scripts/package.sh`
без `task/`, ожидается **1207 passed, 1 skipped**: пропускается тест decision-сервиса, которому нужны
исходные данные и модель.

### Исходные данные

Выданный организаторами каталог `task/` занимает 331 МБ и в репозиторий не входит. Положите
его в корень проекта так:

```
task/
  data/avt_tags.csv              телеметрия АВТ
  data/242000_tags.csv           телеметрия установки 24-2000
  ЛИМСы ... .xlsx                лабораторные анализы
  Выгрузка ПАК ... .xlsx         поточный анализатор
  Теги_хакатон.xlsx              справочник тегов, листы КИП / ЛА / ПАК / ВАК
  АВТ_схемы.pdf                  технологические схемы
  doc006283…, doc006284…, doc006285….pdf   сканы схем АВТ с короткими тегами (К-10, К-2, К-1)
  Транскрипция_Запись_11_09_Q&A….txt     запись сессии вопросов экспертам
```

Сканы и транскрипция нужны только для чтения человеком; код их не использует.

Команды `scenes`, `screen` и `benchmark` работают **без** `task/`: они целиком сценарные.
Данные нужны только для `train`, `advise`, `vak` и `episodes`.

Замороженные реальные срезы лежат в `artifacts/snapshots/`, а `artifacts/` в Git не входит. После чистого
`git clone` этого каталога нет: `load_snapshots` возвращает пустой список, и все сцены молча становятся
синтетическими — предупреждения не будет. Чтобы сцены и `serve` шли на реальных срезах 2026 года, нужен
либо комплект из `scripts/package.sh` (срезы в него включены), либо свой прогон `uv run neftecode snapshot --all`
с `task/` и `artifacts/model.pkl`.

### Команды

| Команда | Что делает | Нужен `task/` |
|---|---|---|
| `uv run neftecode serve` | **Интерактивная демонстрация**: локальная страница, где условия меняются и пересчитываются на том же ядре; по умолчанию — свежайший замороженный реальный срез, «синтетическое состояние» — по выбору | нет (срезы из `artifacts/snapshots/`) |
| `uv run neftecode scenes` | Шесть сцен демонстрации: нормальный режим (реальный момент), ухудшение сырья (синтетическая), зависший анализатор (реальный 20.07.2026), отказ по данным (реальный 16.04.2026), отключённый резервуар, риск ухудшения качества (реальный 24.07.2026) | нет (срезы) |
| `uv run neftecode snapshot --all` | Заморозить реальные срезы 2026 года из `config/snapshot_moments.json`: состояние, доверие, прогноз, измерения T6/F9/F26, отпечаток модели | да, и `model.pkl` |
| `uv run neftecode tank-check` | Сверить оценку серы резервуара (среднее доверенных ПАК за окно) с пробами ЛИМС 2026 | да, и `model.pkl` |
| `uv run neftecode screen` | Экран оператора по одному сценарию | нет |
| `uv run neftecode benchmark` | Сравнение советчика с сохранением режима и пороговым правилом, плюс два отключения | нет |
| `uv run neftecode train` | Обучение и проверка прогноза на хронологических периодах | да |
| `uv run neftecode advise --at 2026-01-05T08:00:00` | Решение на реальный момент: состояние, прогноз, полный цикл агентов, экран | да, и `model.pkl` |
| `uv run neftecode vak` | Проверка 17 формул виртуальных анализаторов по лаборатории | да |
| `uv run neftecode episodes` | Эпизоды превышений и упреждение тревог по ряду анализатора | да |
| `uv run neftecode agent-demo` | Демонстрация слоя LLM-агентов на детерминированной политике (без сети): trace выбора инструментов, ограничений и проверок | нет |
| `uv run neftecode demo` | Прежний прогонный отчёт по прогнозу и историческому воспроизведению | нет, но полезен после `train` |

Отдельный стек запускается так:

```sh
uv run neftecode-stack --root . --artifacts artifacts
```

Его части можно запускать независимо командами `neftecode-data`, `neftecode-model`,
`neftecode-decision` и `neftecode-gateway`. Полный стек требует `model.pkl`; исходный `task/`
нужен только для `/v1/snapshots` и `/v1/live/advice`. Браузер доступен на
`http://127.0.0.1:8765/`.

Общие ключи: `--out` задаёт каталог результатов (по умолчанию `artifacts/`), `--scenario` —
файл сценария, `--config` — файл эксперимента.

Быстрая проверка без исходных данных:

```sh
uv run neftecode serve
```

Откроется на `http://127.0.0.1:8765/` (порт меняется ключом `--port`). Слева панель условий:
сценарий, сера сырья, пределы продукта, текущий выпуск, запас и доступность резервуара,
исправность источников. Кнопка «Пересчитать» прогоняет изменённый сценарий через тот же
загрузчик и то же ядро решения, что и командная строка; «Сброс» возвращает исходные условия.
Сервер слушает только localhost, внешних запросов не делает, дополнительных зависимостей
не требует.

Без интерфейса то же самое даёт:

```sh
uv run neftecode scenes
uv run neftecode benchmark
```

## Результаты

Всё пишется в `artifacts/` (каталог вне Git).

- `scenes/*.html`, `scenes.json` — сцены демонстрации, по странице на сцену.
- `screen.html`, `screen-<время>.html` — экран оператора: момент решения, что делать, ожидаемый эффект,
  запас до предела, план по времени, остатки, устойчивость, альтернативы, доверие к прогнозу, доверие
  к данным, журнал агентов.
- `benchmark.json` — сравнение стратегий, отключения и границы эксперимента.
- `report.md`, `metrics.json`, `predictions.csv` — проверка прогноза на временных периодах.
- `risk_metrics.json`, `risk_predictions.csv` — отдельное обнаружение превышений.
- `vak_check.json` — результат по каждой формуле ВАК.
- `episodes.json` — эпизоды и упреждение тревог.
- `decision-<время>.json` — полное решение: состояние, прогноз, доверие, план, все проверки.
- `model.pkl`, `manifest.json` — обученные модели и хеши исходников, кода и зависимостей.
- `source_rules.json` — пороги доверия к источникам для `scenes`, `screen`, `serve` и HTTP-сервисов;
  `advise` читает встроенную копию порогов из `model.pkl`.
- `snapshots/*.json` — замороженные реальные срезы для демонстрации без `task/`; привязаны к отпечатку модели.
- `tank_level_check.json` — сверка оценки серы резервуара с лабораторией.

Экран оператора подписывает «Момент решения» (или явно «неизвестен»), а у каждого источника показывает возраст,
в том числе у исправного реального среза: «ЛИМС пригоден · возраст 17.0 ч из 48.0 ч»
(у синтетической демосцены — 5.0 ч). Отдельная карточка «Доверие к прогнозу»
даёт точечный прогноз серы, нижнюю и верхнюю границы интервала, заданное покрытие и покрытие на отложенной
проверке; с пределом серы сравнивается **верхняя граница интервала, а не точечный прогноз**, а при покрытии ниже
заданного печатается предупреждение, что интервал на истории оказался узким. На сценарных прогонах, где прогноз
не считался, карточка вырождается в «Прогноз серы не рассчитывался». Экран отказа тоже показывает ключевые
текущие параметры и состав смеси сейчас: оператору нужно видеть, от чего отсчитывается решение, даже когда
предлагать нечего.

## Как устроено

Для локального запуска компоненты доступны как четыре отдельных процесса: data (8766),
model (8767), decision (8768) и gateway (8765). Gateway сохраняет браузерный `/api/*`
контракт, evaluation остаётся batch CLI. Сценарная демонстрация работает без `task/`.

Одно расчётное ядро, которое вызывают и CLI, и экран оператора, и демонстрация. Код разделён
по Clean Architecture: внешние слои используют прикладные сценарии, а бизнес-правила не зависят
от файлов, ML, HTTP и интерфейса.

```
src/neftecode/
  domain/          сущности и правила мониторинга, производства и советчика
  application/     MakeDecision, PlanOperation, GetLiveAdvice, ReplayDecisions и порты
  infrastructure/  CSV/XLSX/JSON, модели прогноза, live-адаптеры и артефакты
  evaluation/      benchmark, ВАК, эпизоды, лаги и устойчивость
  presentation/    CLI, HTTP, HTML и демонстрационные сцены
  services/        отдельные data/model/decision/gateway процессы и supervisor
  composition/     сборка зависимостей и обработчики команд
  bootstrap.py     совместимая точка запуска CLI
```

Направление зависимостей проверяется отдельным AST-тестом:
`presentation`, `infrastructure` и `evaluation` обращаются к `application`, а `application` —
к `domain`. Внешний `composition/` подключает конкретные адаптеры; внутренние слои его
не импортируют. Старые плоские модули удалены; публичные функции `bootstrap` сохранены. JSON решений и команды CLI
сохранены без изменения.

### Слой LLM-агентов (включён всегда)

Поверх детерминированного контура добавлен ограниченный multi-agent слой: `OrchestratorAgent`,
`QualityAgent` и `ReliabilityAgent` — настоящие tool-using агенты на языковой модели. Они рассуждают и
выбирают инструменты; числа, допустимость, ранжирование, финальную перепроверку и устойчивость считает
код. Модель не может ослабить ограничение: ей доступен закрытый словарь только ужесточающих фильтров
(минимальный запас качества, число изменений, запрет присадки, загрузка отбора, только постоянные планы,
время до нарушения, требование устойчивости). Выбор среди допустимых делает прежнее `rank()`, выбранный
план проходит тот же `release` (упреждение, финальная перепроверка Gate, устойчивость) и повторную оценку
новым экземпляром планировщика. Повторная оценка **не независима**: `application/agentic/decision.py` строит
`PlanOperation(self.scenario)` на том же объекте сценария и тех же входах, то есть прогоняет тот же
детерминированный код. Поймать она может только утечку состояния или ошибку кеширования между прогонами;
ошибку моделирования — не может. Вдобавок она смотрит лишь на `evaluation.feasible`, а не на `passes_review`,
как остальной код. Любой сбой модели — таймаут, лимит, сломанный JSON, исчерпанный бюджет — возвращает
детерминированное решение.

```sh
uv run neftecode screen                                    # агенты включены: Z.AI Coding Plan, glm-5.3-flash
LLM_PROVIDER=scripted uv run neftecode screen              # детерминированная политика вместо модели, без сети
AGENTIC_DECISION_ENABLED=0 uv run neftecode screen         # явное отключение: прежние решения байт-в-байт
uv run python scripts/agent_live_smoke.py                  # сухой прогон настроек, без сети
```

Агенты работают при каждом решении (`serve`, `scenes`, `screen`, `advise`, decision-service); benchmark и
replay остаются детерминированными. Решение с живой моделью занимает минуты (10–45 с на вызов модели), поэтому
gateway и страница ждут decision до `AGENT_TIMEOUT_SECONDS + 60` с (660 с при умолчаниях). Нет ключа или
провайдер недоступен — выдаётся детерминированное решение с пометкой `fallback`; экран показывает это в карточке
«Агентный слой» вместе с причиной. Набор тестов фиксирует `AGENTIC_DECISION_ENABLED=0` (`tests/conftest.py`),
чтобы сравнивать решения с эталонными и не обращаться к модели.

**Набор переменных для защиты** — `config/demo.env.example`. Умолчания (`LLM_REQUEST_TIMEOUT_SECONDS=120`,
`LLM_MAX_RETRIES=1`) рассчитаны на медленного, но живого провайдера; в сети, которая молча глотает пакеты
(поведение заводского firewall), они дают 241 с на один вызов — замер 18.09. Для показа:

```sh
export LLM_REQUEST_TIMEOUT_SECONDS=30 LLM_MAX_RETRIES=0 AGENT_TIMEOUT_SECONDS=180
uv run neftecode serve                        # провайдер недоступен → детерминированный ответ за ~30 с, на экране fallback
LLM_PROVIDER=local uv run neftecode serve     # закрытая сеть: локальная OpenAI-совместимая модель
LLM_PROVIDER=scripted uv run neftecode serve  # без модели вообще: детерминированная политика агентов
```

Полный отказ DNS обнаруживается за ~1 с и в настройке не нуждается.

Настройки — переменные окружения (`LLM_PROVIDER`, `ZAI_API_KEY`/`TOKEN`, `ZAI_MODEL`, `ZAI_BASE_URL`,
`OPENAI_*`, `ANTHROPIC_*`, бюджеты `AGENT_*`); ключи только в окружении или `.env`, который не коммитится.
Провайдеры: Z.AI Coding Plan (по умолчанию), `local` — OpenAI-совместимая модель внутри закрытой сети завода
(Q&A 11.09: интернета нет, локальная LLM до ~30B; `LOCAL_LLM_MODEL`, `LOCAL_LLM_BASE_URL`, ключ не нужен), OpenAI и
Anthropic. На заводе без интернета Z.AI недоступен — нужен `LLM_PROVIDER=local`, иначе агенты уйдут в `fallback`. Демонстрация
(`serve`, `scenes`) идёт на замороженных реальных срезах 2026 года через тот же связыватель, что и `advise`; на экране
подписано, реальный это срез или синтетическое состояние, и откуда пороги доверия. Бюджет одного решения мал: не больше 12 вызовов модели, shortlist из 5
кандидатов, компактный контекст, предел ответа модели 6144 токена (`LLM_MAX_TOKENS`); сырые ряды и полные
траектории модели не передаются. Предел поднят с 2048 после единичного наблюдения в живой сессии
17.09 на `zai`/`glm-5.3-flash`: один ответ специалиста был оборван по длине (finish reason `length`),
после чего вердикт стал `UNKNOWN` с уверенностью 0; повтор того же сценария с 6144 вернул оба мнения.
Это оперативное наблюдение не заморожено как сравнительный артефакт, поэтому частота таких отказов
не заявляется. Подробности —
`plan/01-target-agent-architecture.md` и `plan/04-agent-contracts.md`.

Прогноз по истории и модель последствий действия — **разные компоненты**. Прогноз отвечает,
что будет при наблюдаемом ходе событий; модель последствий — что получится, если сдвинуть
уставку. Подмена одного другим запрещена: CatBoost с заменённым входом моделью управления
не становится.

## Главные результаты и их границы

- **Прогноз серы выбран по пяти rolling-полугодиям до 2026.** Причинная поправка
  `last_pak_bc = ПАК + median(20 последних доступных ЛИМС−ПАК)` снизила средний MAE 1.582 → 1.415 мг/кг
  (разность −0.167; парный bootstrap 95% CI [−0.232; −0.096]), долю фактов выше upper 6.64% → 4.74%
  и верхний запас 4.062 → 3.965 мг/кг. Это единственный кандидат, прошедший заранее записанное правило;
  CatBoost остатка и адаптивная граница сохранены как отрицательные результаты. Прежний fixed-validation аудит
  всё ещё выбирает `last_pak` (1.363 против 1.374 у поправки), но не переопределяет rolling-решение.
  В единственном финальном прогоне 2026 поправка дала MAE 1.616 против 1.802 (разность −0.186;
  95% CI [−0.302; −0.071]) и сузила upper margin 4.283 → 3.632, однако `exceed_upper` остался
  выше цели: 6.01%. Поэтому диапазон — эмпирическая оценка, не гарантия 95%.
  Для T95 простой прогноз выигрывает заметно: 4.849 против 8.076 у CatBoost.
- **Отклик серы на температуру входа реактора оценивается по данным при обучении.** `train` считает β на `ht.T6` тем же
  ARX, что в исследовании (плато 3–8 ч, окно 12 мес., строгий отбор строк), по данным до `train_end` и на сетке τ
  (1 января / 1 июля) и пишет `artifacts/response_model.json`; живое решение берёт последнюю оценку, сделанную строго до
  момента. После причинного расчёта порога F9 на данных только до τ−6 ч окно 2025
  (τ = 2026-01-01) даёт β = −0.423 [−0.477; −0.389], края следующего
  полугодия −0.217 / −0.739, область T6 342.9–386.1 °C, F9 150.3–256.7 т/ч, |ΔT| ≤ 2 °C (`RESPONSE_MODEL_T6.md`;
  объявленная политика — `config/response_model.json`). Эффект хода T6 не засчитывается раньше 3 ч, в пределах горизонта —
  не больше 0.66 хода; ход T6 допускается, только если проходит проверки и при слабом крае β; возмущения отклика,
  не действующие на hold, в устойчивость не входят. Вне области или без измерения T6 числовая уставка не предлагается.
  Отклик по расходу не идентифицирован (`open`).
- **Живое решение стоит на измерениях, а не на сценарных уставках.** На момент решения в сценарий подставляются
  `ht.T6` (температура входа Р-202), `ht.F9` (массовый расход сырья) и `ht.F26` (расход гидроочищенного ДТ → приток
  резервуара); окно оценки серы резервуара = запас / приток. На 2026-01-05 08:00: T6 367.8 °C (сценарий говорил 348),
  приток 204 т/ч (сценарий — 95), окно 19.6 ч (было 42), сера резервуара 4.56 мг/кг (было 5.19); решение — hold.
  Вклад верхней границы прогноза в серу резервуара за 3 ч при таком притоке ≈ 0.89 мг/кг.
- **Оценка серы резервуара непроверяема выданными данными.** `tank-check` на 2026: последний ПАК против пробы ЛИМС в
  момент отбора — MAE 1.35, r 0.53; среднее за окно 19 / 42 ч — r 0.17 / −0.01: проба описывает поток, не парк.
  Побочный факт: в 2026 ПАК систематически ниже ЛИМС на ≈ 0.4 мг/кг — почти весь технологический запас 1 ppm.
- **Цетановое число не моделируется.** В пакете 42 анализа; обученная модель по ним не заявляется.
- **Ни одна формула ВАК не принята как оценка качества.** По официальному файлу формул от 16.09 (в нём четыре
  формулы АВТ отличаются от листа, разобранного раньше): две не вычисляются (вход `LIMS:...Pipeline...` не привязан),
  одна не с чем сверить, 14 сверены с лабораторией — корреляция от −0.11 до 0.54; порог 0.5 прошли `AVT6:350:T50`
  (0.515; MAE 4.778 против 8.229 у медианы) и `24-2000:GODT:IBP` (0.539; MAE 5.646 против 5.403).
  Первая опирается на неподтверждённую привязку фракции АВТ к точке ЛИМС и оценивает T50, вторая проигрывает
  медиане; ни одна не даёт требуемый показатель товарного ДТ. Поэтому ТЗ-шный третий источник качества
  (ВАК) не используется.
- **Сценарный результат пересчитан после исправления баланса запасов.** В `sour_crude`
  сохранение режима нарушает 7 проверок, пороговое правило — 15. Советчик даёт 180 т без
  нарушений; без переходного планирования тоже 180 т. Прежний выигрыш переходов не подтверждён.
  Если убрать правило конечного резерва, видимый выпуск вырастает до 240 т.
- **На нормальном режиме есть проигрыш.** Пороговое правило дешевле: 1.05 против 1.09 на тонну,
  резерв не расходует, а советчик сохраняет режим. `artifacts/benchmark.json` фиксирует эти результаты,
  но не содержит порога или вычисленного объяснения причины `hold`; поэтому доля экономии здесь не заявляется. То же в сценарии
  зимнего ДТ (`winter_grade`): в бенчмарке 5 сценариев, 6 выигрышей и 4 проигрыша по метрикам.
  При достаточном резерве обе стратегии дают 300 т с одним изменением.
- **План может быть хрупким.** В `sour_crude` объявлено 8 отклонений, проверяемы 6: выдержано 4,
  нарушено 2, ещё 2 к плану неприменимы (нет хода уставок ГО). На экране это записано как
  «4 из 6 заданных отклонений выдержано, 2 к плану неприменимы», план выдаётся с предупреждением.
  Это не вероятность успеха и не гарантия безопасности.
- **Сцена риска по качеству идёт на реальном срезе.** Шестая сцена «Риск ухудшения качества» стоит на
  замороженном срезе `20260724-030000` (24.07.2026 03:00, обоснование момента — `config/snapshot_moments.json`),
  статус `recommend_scenario`. Поточный анализатор показывает 14.637 мг/кг внутри устойчивого превышения
  24.07 00:00–04:10 (4.167 ч по разнице крайних точек, пик 14.811, среднее 12.415); прогноз — 14.933 мг/кг с интервалом 10.570–20.942
  при пределе 10 мг/кг. Источники исправны (ЛИМС 23.07.2026 10:00 = 6.4 мг/кг, возраст 17 ч; анализатор
  не завис; пропусков телеметрии 1.04%), поэтому сцена про качество, а не про данные. При сохранении режима
  смесь резервуара выходит за предел через 5 ч — раньше запаса реакции 12 ч, поэтому ядро рекомендует план
  c0041: рецепт меняется с main 0.9 / reserve 0.1 на main 0.7 / reserve 0.3, уставки остаются на измеренных значениях,
  нарушение отодвигается на 12 ч. Это та сцена, которой закрывается требуемый ТЗ «период с риском ухудшения
  качества».
- **Проверка на реальных данных 2026 года** (`context/advisor-study-2026-09-15.md`). Прогноз серы
  питает приток основного резервуара, серу содержимого система оценивает по 42 ч доверенных показаний,
  за горизонтом план продолжается на 48 ч. Исторический прогон T55 на 250 случайных моментах дал
  216 `hold` (86.4%) и 26 отказов по данным (10.4%); таблица и протокол выборки сохранены в
  `context/advisor-study-2026-09-15.md`, сырые записи — в `experiments/advisor-study-random-2026-09-15.jsonl`.
  Отказы связаны с зависшим анализатором и ЛИМС старше 48 ч; ещё в 3% случаев не было оценки резервуара.
  Зафиксирован один совет, вероятно лишних советов нет.
  Эти прогоны сделаны до 17.09, то есть до удаления 307 и вывода порогов из данных; их нужно повторить.
  По 12 устойчивым эпизодам анализатора: совет в 10, в 4 — за 4–11 ч до начала; предупреждение до начала — в 9.
  Лаборатория подтверждает превышение потока лишь в одном эпизоде, товарная смесь не измерялась.
- **Частота советов зависит от допущений.** Окно оценки резервуара 24–72 ч почти не меняет решения; объём
  резервуара и запас реакции меняют всё: 0 советов при 6 ч или 8000 т, 49 из 140 при 24 ч или 2000 т.
  Эти параметры должен задать завод.

Все числа сравнения получены в нашей сценарной модели, не на заводе. Набор сценариев мал и
выбран нами; поиск ограничен бюджетом. Выпуск стоит первым в правиле сравнения, поэтому
отдельно показываем стоимость, расход резерва и число изменений. Период 2026 уже просматривался;
это исторический ориентир, а не новый слепой тест.

Приток постепенно меняет массу и свойства резервуара: запас 4000 т не становится новым потоком
мгновенно. Внутри шага сначала отбирается исходная смесь, затем смешивается приток; расход притока
задан сценарием. T95 и цетан усредняются по объявленной сценарной линейной модели, плотность — по
аддитивности объёмов (масса, делённая на сумму объёмов). В simulated
replay тот же баланс применяется только к текущей подтверждённой операции. После сохранения и
продолжения сохраняются часы, запасы и возраст действий. Snapshot без журнала действий считается
установившимся режимом; журнал действий нужен для ещё не завершившихся откликов.

## Что не доказано

1. Объём резервуара 4000 т, резервный и лёгкий компоненты, вместимость парка — параметры завода, в данных их нет
   (`config/parameters.json`, `tank_farm_and_response`); частота советов определяется ими напрямую (8000 т → 0 советов
   из 140, 2000 т → 49). Приток резервуара и окно перемешивания — из данных, но при отборе 100 т/ч запас растёт на
   ≈ 110 т/ч без заданной вместимости. Вопросы подготовлены к сессии 18.09.
2. Эталона для товарной смеси нет: ЛИМС и анализатор меряют поток после гидроочистки; оценка содержимого резервуара
   проверена только в вырожденном случае и с лабораторией не согласуется (см. `tank-check`).
3. Отклик АВТ на изменение уставок — сценарная модель; тегов печей К-2 в данных нет. Отклик ГО по температуре — из
   данных, с дрейфом до ×1.7 между полугодиями; по расходу — не идентифицирован.
4. Поправка смещения причинна и улучшила rolling-MAE, но верхняя граница не гарантирует заявленную цель:
   в единственном финальном прогоне 2026 выше неё оказались 6.01% доступных проб, двустороннее покрытие — 87.1%
   вместо 90%. Локальная ошибка rolling по окну 30 проб доходила до 20%; выбирать параметры по 2026 запрещено.
5. Модель доступна только с 2026 года, который уже просматривался; запас реакции 12 ч выбран после
   пробного прогона.
6. Польза LLM-агентов не измерена. Проверено другое: они не могут выдать план, не прошедший Gate, и любой их
   сбой оставляет прежнее детерминированное решение. Демонстрация `agent-demo` идёт на заранее написанной
   политике (`provider=scripted`), это не работа языковой модели. Живых запусков было два (Z.AI Coding Plan,
   `glm-5.3-flash`, 2026-09-16): первый провайдер отклонил по лимитам плана, во втором модель действительно
   работала как агент — сама выбрала инструменты и обосновала вердикт ссылками на их результаты, но решение
   упёрлось в бюджет времени (10–45 с на вызов) и слой вернул детерминированный hold. Ни одного живого прогона
   до конца цикла пока нет.

7. Третий источник качества из ТЗ не подключён: приоритет реализован как ЛИМС → ПАК, без ВАК. Формулы ВАК
   проверены и как измерение непригодны (`context/vak-review.md`), поэтому значение из ВАК в решение не попадает.
   Это объявленный пропуск, а не забытый: подключать источник, не воспроизводящий лабораторию, мы не стали.
8. Соотношение ВСГ/сырьё, названное в ТЗ среди возможных воздействий, не моделируется. `ht.F2` — расход газа
   на линии от ЦК-201 и кандидат на циркуляционный поток, `ht.F25` — свежий ВСГ. Для F2 не подтверждены границы
   линии и прохождение всего потока через Р-202; для отношения `F2/F9` нет безопасного диапазона управления
   и идентифицированного отклика серы. Поэтому F2 используется только как признак режима и фильтр работы,
   а воздействие в оптимизатор не добавляется (`context/decisions-2026-09-18.md`).
9. Давление колонны АВТ и давление ГО не добавлены как управляемые воздействия. У ближайшего тега АВТ
   `avt.P22` не подтверждена единица и есть аномальный хвост; для подтверждённого `ht.P13` нет безопасного
   диапазона хода и модели отклика качества. Они остаются наблюдаемыми параметрами, а не уставками оптимизатора.
10. Тяжесть режима — третий критерий строгого порядка после выпуска и условной стоимости; она влияет
    только при точном равенстве двух старших критериев. Парето-фронт из необязательной части ТЗ не строится:
    завод не задал веса или правило выбора между этими целями (`context/decisions-2026-09-18.md`).

Корректная формулировка: система на реальных данных ведёт себя последовательно и безопасно при явных
допущениях о резервуарах; соответствие реальному заводу требует данных о резервуарах и смешении.

## Открытые вопросы

Официальный справочник тегов 24-2000 (16.09) закрыл вопрос смысла: температура входа Р-202 — `T6` (медиана 362.7 °C),
`T11` — выход Р-202, `P8` — перепад давления, `F9`/`F15` — расход сырья, `F26` — расход гидроочищенного ДТ
(`context/materials-2026-09-16.md`). Масштаб `F15` (медиана ~3400 м³/ч) не согласуется с массовым расходом и не является пересчётом единиц
(`context/response-research/t6/f15_scale.md`); расход берётся из `F9`. Модель отклика на `T11` опровергнута и пересчитана на
`T6` (`RESPONSE_MODEL_T6.md`); в живом решении используется как линеаризованный наклон с областью применимости. Не привязаны `LIMS:24-2000.Pipeline.D15` и `...95%.T`. Предел T95 не задан
ни ТЗ, ни экспертами (в сценарии 360 °C); плотность и цетановое число — по сообщению 582 (летнее ДТ 820–845 и ≥ 51,
зимнее 800–845 и ≥ 49, сценарий `winter_grade`). Технологический запас по сере на установке — 1–2 ppm (Q&A 15.09):
при меньшем запасе оператор получает предупреждение, жёсткий предел остаётся 10 мг/кг. Между АВТ и ГО стоит парк с
временем пребывания от часов до суток, а в сценариях лаг АВТ 0.5 ч — это расхождение пока не устранено. Кривая эффекта
присадки от дозы не предоставлена.

Схемы АВТ с короткими тегами показали, что английские имена переменных схемы стоят на разных
приборах, а у выходов атмосферных печей К-2 номеров тегов нет. Поэтому модель АВТ остаётся сценарной
и текущие значения из CSV в неё не подставляются. На установках работают регуляторы с обратной связью:
совет формулируется как «сохранить/изменить уставку регулятора», контур описан в сценарии (`actuation`),
динамика контура не моделируется.

Детерминированный контур работает локально без интернета и внешних API. Слой LLM-агентов по умолчанию
ходит в Z.AI; в закрытой сети завода его переключают на внутреннюю модель (`LLM_PROVIDER=local`), без модели
он возвращает детерминированное решение с пометкой `fallback`. Эксперты назвали запуск в закрытой среде
критерием оценки.

Подробности — `context/requirements-map.md`, `context/avt-schemes-2026-09-14.md`,
`context/qa-session-2026-09-11.md` и `config/parameters.json`.

## Комплект сдачи

```sh
bash scripts/package.sh
```

Скрипт собирает `dist/neftecode-<время>.tar.gz` из отслеживаемых Git файлов и результатов
прогона. В комплект не попадают выданные данные `task/`, виртуальное окружение и кэши; сборка
прерывается, если что-то из этого просочилось или нашлось похожее на секрет. Комплект проверен
распаковкой в чистый каталог: `uv sync --frozen`, полный тест и запуск сервисного стека
проходят без исходных данных; проверка реального live-контракта пропускается без `task/`.
`uv run neftecode scenes` также отрабатывает без исходных данных. Отправка организаторам скриптом
не выполняется и делается только вручную.

## Известное неудобство

При работе с данными pandas выдаёт `DeprecationWarning` про generic-единицу numpy timedelta.
Предупреждение приходит из самой библиотеки, а не из нашего кода: его даёт любой вызов
`pd.Timedelta`. Версии зафиксированы в `uv.lock`, поэтому поведение воспроизводимо; при
будущем обновлении pandas и numpy это место потребует внимания.
