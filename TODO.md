## B0. Offline и React — РЕШЕНО

**Вопрос был: можно ли фронтенд-библиотеки, если требование — работа без интернета.**
Ответ: **можно, библиотеки offline не нарушают.** Требование организаторов (Q&A 11.09) —
чтобы **запуск** работал в закрытой сети. Оно ничего не говорит о том, чем мы пользуемся
при разработке. Нарушает offline не React, а **внешний запрос из браузера в рантайме**:
CDN, Google Fonts, облачные чарты.

**Принятое решение:**

1. Исходники React/TS лежат в `src/frontend`, зависимости ставятся `npm` **у нас**
   (Node v24 и npm 11 на машине проверены, реестр доступен).
2. Результат сборки — самодостаточные файлы **без единой внешней ссылки** — **коммитится
   в репозиторий** в `src/neftecode/presentation/web/static/`.
3. Python отдаёт эту статику как файлы. У жюри: `uv sync --frozen` → `uv run neftecode serve`,
   **без Node, без npm, без сети**.

**Почему не иначе.** Отдавать фронт из исходников — значит требовать Node и `npm install`
у жюри, это прямо ломает критерий. Оставить инлайн-HTML — отклонено пользователем.

**Что это накладывает:**

- **Библиотеки можно, но экономно**: каждая уезжает в бандл и в Git. Роутер и state-менеджер
  для одностраничного лендинга не нужны.Чарты — **свои инлайн-SVG**, не библиотека:
  это и меньше веса, и полный контроль над читаемостью с проектора.
- **Шрифты только системные.** `@font-face` с внешним URL — нарушение; шрифт файлом в бандле —
  это лишние сотни килобайт в Git ради малого.
- **Проверка обязательна:** после сборки — grep по бандлу на `http://`, `https://`, `//cdn`,
  `fonts.googleapis`. Ни одного вхождения.

**Критерий.** На машине без интернета и без Node: `uv sync --frozen` → `uv run neftecode serve` →
лендинг открывается полностью, DevTools не показывает ни одного внешнего запроса.

# Синхронизация между дорожками

Файлы, которых касаются обе дорожки, — только по очереди, с явной передачей:

| Файл | Владелец | Когда отдаёт |
|---|---|---|
| `context/state.md` | A | B пишет только свой раздел, после коммита A |
| `context/defence.md` | B | A даёт числа после A7/A8 |
| `README.md` | B | A даёт числа после A1/A7 |
| `presentation/web/*`, `src/frontend/*` | B | A не трогает; B6 ждёт решения A3/A4 |
| `config/scenarios/*.json` | A | B только читает |
| `explain.py` | A | B просит поля, A их добавляет (A5b-1, A5b-3, A5b-4) |
| `.gitignore`, `scripts/package.sh` | B | правки под сборку фронта (B0a) |

**Честно про параллельность: её почти нет.** B стартует после A0b; B1/B2 рисуют поля,
которые A добавляет в A5b; B6 ждёт нерешённую A3; B7 ждёт A8; B9 ждёт A7. Реально независимой
работы для второго агента — **6–10 часов из четырёх дней**. Заявлять «две равные дорожки»
было самообманом.

**Как делить на самом деле.** Не «ядро и фронт», а **«ядро» и «всё, что не трогает
`src/neftecode`»**:

- **Агент 1 (ядро):** A0, A2, A1, A2b, A3, A4, A5b, A6, A7, A8 — весь критический путь.
- **Агент 2 (без кода ядра):** B0a (ловушки сборки + Google Fonts), B8 (обоснование β),

**Что нельзя потерять при переходе на новый стиль:** честность интерфейса. Бейджи происхождения

## W1. Этап конфигурации и запуск по кнопке

- На входе виден **только первый экран**: выбор сценария, момент решения, отказ источника,
  изменяемые условия (сера сырья, пределы продукта, доступность резервуара, выпуск).
  Остальные семь этапов скрыты до запуска.
- Кнопка **«Запустить»** — заливка Carbon Warm, пилюля 100px по системе.
- После запуска страница **сама прокручивается** к текущему этапу, этапы появляются по очереди.
- Повторный запуск с другими условиями — без перезагрузки страницы.

## W2. Состояния этапа и их визуальное различие

Четыре состояния, различимые с проектора и в монохроме:
`pending` (ещё не начат) — приглушённый, рамка пунктиром;
`running` (идёт) — активная рамка, бегущий индикатор, номер этапа выделен;
`done` (готов) — обычный вид, данные раскрыты;
`failed` / `refused` — статусный тон (узкое исключение системы), причина текстом.

Индикатор выполнения — **без вращающихся спиннеров**: по V1 движение служит пониманию.
Подойдёт бегущая полоса по верхней кромке или пульс метки этапа.

## W3. Поток выполнения — откуда брать данные

**Важно:** сервер сейчас отдаёт готовое решение одним ответом `/api/decide`. Настоящая поэтапность
требует либо потоковой отдачи (Server-Sent Events / chunked), либо разбиения на шаги.

Решение принимать по коду, варианты:
(а) **SSE-поток** от `serve`: сервер шлёт события по мере прохождения этапов — честнее всего,
    но требует правки HTTP-слоя (`presentation/web/server.py`, stdlib `http.server`);
(б) **Пошаговые запросы**: фронт запрашивает этапы по очереди — проще, но сервер всё равно
    считает решение целиком;
(в) **Проигрывание готового результата** с задержками — выглядит живо, но это инсценировка.

**Если выбран (в) — обязательно пометить на экране**, что это воспроизведение уже посчитанного
решения, а не ход расчёта в реальном времени. Выдавать инсценировку за живой расчёт нельзя:
это ровно тот риск R16, из-за которого мы маркируем `scripted`.

## W4. Трасса агентов — показывать по-настоящему

- Сообщения агентов появляются **по мере поступления**, а не пачкой в конце.
- Видно: кто спрашивает (оркестратор), кого (качество / надёжность), какой инструмент вызван,
  что вернул, какой вердикт и почему.
- Сырой JSON каждого шага раскрывается на месте (уже есть).
- **Маркировка провайдера остаётся обязательной**: при `scripted` — «детерминированная политика,
  не языковая модель»; при живой — имя модели и счётчики вызовов/токенов.
- Живой прогон на модели возможен: ключ Z.AI в `.env`, проверен 19.09 (HTTP 200).
  Команда `agent-demo` **всегда** идёт на демо-политике по замыслу; живой путь — `screen`
  и `serve` через `default_decision_factory`.

## W5. Левая панель — сделать содержательной

Сейчас это просто список из восьми ссылок. Что можно показать помимо навигации:
состояние этапов (готов / идёт / отказ), ключевые числа по мере появления (вердикт, выпуск,

Панель остаётся липкой, на узком экране сворачивается.

## W6. Кастомные скроллы

Во всех прокручиваемых областях (страница, таблицы `.scroller`, JSON-панели) — собственный
вид полосы прокрутки в палитре системы: `scrollbar-width`/`scrollbar-color` плюс
`::-webkit-scrollbar` для Chromium. Полоса не должна съедать контраст и обязана оставаться
видимой: невидимый скролл скрывает от оператора, что содержимое прокручивается.

## W7. Что визуализировать сверх текущего

По возможности и без выдумывания данных, которых нет в payload:
траектория серы по горизонту с пределом (есть); разбор тяжести режима по слагаемым и весам (есть);
сравнение альтернатив по критериям с величиной разрыва (есть); возраст и пригодность источников
(есть); чувствительность к оценке резервуара (добавлена задачей A5); отсев кандидатов по раундам
вето (есть в трассе оптимизатора).

**Ограничение:** рисовать только то, что реально лежит в payload. Пустой блок пишет
«не передавалось», а не имитирует данные.

**Ограничения дорожки W:** ноль комментариев, файлы ≤250 строк, именованные экспорты,
никаких внешних запросов, честность интерфейса выше красоты.
