# Фронтенд для экспертной демонстрации

Дата: 2026-09-21. Это задачи на реализацию, не отчёт о выполнении. Основание: исходное ТЗ
`task-review/spec-text.txt`, текущие компоненты и контракты frontend/backend, проверенные прогоны.
Цель: эксперт запускает цикл и понимает причину → действие → ожидаемый результат → ограничения,
видит обмен информацией между агентами и может проверить выбор. Новое ядро не требуется.

## Что сейчас мешает

- Большая схема занимает основную площадь, но сама по себе не объясняет предпочтительность плана.
- `OperatorAnswer` повторяет длинный `decision.reason`; `mandatoryNote()` выделяет только первый
  критический риск. Второе существенное ограничение остаётся внутри длинного текста.
- Номинальная допустимость, устойчивость к возмущениям и готовность к промышленному применению
  выглядят как противоречащие друг другу вердикты.
- «20 событий агентов» не показывает ни содержания консультаций, ни влияния специалистов.
- «8 из 8 этапов» включает пропущенные стадии. Анимация `revealQueue` добавляет 450 мс между
  показами; `useRun` может получить результат раньше завершения визуального показа.
- `healthy` подписан «все источники исправны», хотя в backend это отсутствие искусственно внесённого
  отказа (`SOURCE_FAULTS.healthy = {}`), а исторический срез может содержать плохие источники.
- Макет молча подставляет другой срез, если заданного нет; быстрые переключения могут завершить
  запросы условий в обратном порядке. Это угрожает достоверности названия выбранной сцены.

## Компоновка: один рабочий экран

На ширине 1440 px: компактная панель условий сверху; под ней две колонки примерно 60/40.
Слева ответ оператору, затем сравнение вариантов. Справа ход расчёта и карточки агентов.
Под ними раскрываемые доказательства. На узком экране тот же порядок в одну колонку.

До запуска: сцена, историческое время, внесённые изменения, режим агентов, кнопка запуска.
Во время расчёта: компактный прогресс и фактический обмен агентов; будущего вердикта ещё нет.
После расчёта: крупный ответ, конкретное действие, причина выбора, все существенные условия.
Полная техническая схема остаётся в «Как получено решение», доступном за один клик.
Не делать отдельную витрину, длинную посадочную страницу или второй конкурирующий dashboard.

## Последовательность задач

### F01 · P0 · Единый смысл статусов

Сначала создать общий адаптер представления результата, используемый карточкой ответа, схемой и итогом.
Backend-статусы и исходные тексты сохраняются для аудита; русский текст строится по структурным полям.

| Условие | Заголовок | Дополнительное состояние |
|---|---|---|
| `status=refuse` | Решение не выдано | Причина отказа и что требуется для повторного расчёта |
| `status=hold` | Сохранить режим | Ограничения и предупреждения, если они есть |
| `status=recommend_scenario` | Предложен сценарный план | При существенных рисках: «Есть ограничения» |
| Ошибка транспорта/расчёта | Расчёт не завершён | Ошибка и повтор запуска; это не технологический отказ |
| Остановка пользователем | Расчёт остановлен | Нельзя показывать как отказ или успешное завершение |

Отдельно показывать: «Номинальные проверки», «Устойчивость к отклонениям», «Данные и допущения».
`gate.feasible=true` не означает прохождение стресс-проверок. `deployment_readiness.ready=false`
и запрет товарного выпуска относятся к области применения прототипа, а не к причине каждого отказа.
Все существенные `explanation.risk.items` показывать компактно, не выбирать один через `.find()`.
Не называть выполненными неизвестные проверки. Не превращать предупреждение в разрешение применить план.

Приёмка: риск-сценарий показывает и снижение подачи резерва −20%, и чувствительность к составу
резервуара. Отказ на данных показывает отсутствие пригодных источников и что поиск не проводился.
`hold` с предупреждением не становится безусловно зелёным «всё безопасно».

### F02 · P0 · Достоверный запуск и завершение

Оставить один основной запуск и три пресета. Для каждой сцены явно указать срез и искусственные
изменения. `healthy` назвать «Без внесённых отказов»; реальное качество источников брать из результата.
Если нужного среза нет — показать недоступность сцены, не подменять его молча.
Защитить загрузку условий от устаревших ответов: AbortController или идентификатор запроса.
Зафиксировать условия запущенного расчёта отдельно от редактируемых, связать результат с ними.

Завершать состояние расчёта по успешному получению/закрытию протокола, а анимацию отделить от времени
backend. Не показывать готовый ответ одновременно с надписью «Пайплайн работает» из-за очереди показа.
Вместо «8/8» при отказе: «Расчёт завершён · поиск и агенты не запускались»; в деталях — реальные
выполненные/пропущенные этапы. Не считать количество этапов процентом вычислительной работы.
Не создавать фиктивные агентные события; факт выполнения брать из событий/трассы и результата.
Проверить `stageRan`: отсутствие финального Gate не доказывает, что прогноз никогда не выполнялся;
отсутствие мнений специалистов не доказывает отсутствие вызовов оркестратора при fallback.

Приёмка: быстрое переключение трёх пресетов не смешивает условия; двойной запуск, остановка, ошибка
сети и поздний ответ предыдущего запуска не подменяют текущий результат. Пропущенные этапы не зелёные.

### F03 · P0 · Собрать основной экран вокруг ответа

Внедрить компоновку выше. Свернуть большие сценарные карточки в компактный переключатель с коротким
описанием выбранного случая. Сохранить кнопку запуска на виду. Не перехватывать прокрутку пользователя
автоматическими прыжками между схемой и ответом; результат появляется в стабильном месте.

Ответ состоит из четырёх коротких частей: проблема; действие; почему выбран план; условия/ограничения.
Изменения показывать строками «параметр · сейчас → предложено · единица». Доли можно отображать
процентами с корректной конвертацией. Источник текущего режима:
`explanation.current_operation ?? decision.current_operation`; целевой — `immediate_action`.
Последующие шаги брать из `selected_plan.steps`, отдельно от немедленного действия.
Полный backend-текст доступен в деталях, без дублирования предупреждений на главном экране.

Приёмка: на 1440×900 без прокрутки видны сцена, запуск/статус, итог, действие и существенные
ограничения; при большом объёме рисков допускается рост карточки, скрывать их ради высоты нельзя.
На 1280×720 и 390 px нет горизонтального скролла, наложений и обрезанных действий.

### F04 · P0 · Показать вклад агентов

Три компактные карточки реальных ролей: оркестратор, качество, надёжность. Во время выполнения —
последний подтверждённый запрос/ответ. После — «что проверил → что заключил → что изменилось».
Данные: `run.agentEvents`, `agentic.opinions`, `constraints_applied`, `vetoed_candidates`, `final`,
`outcome`, `fallback_reason`. Предложенное ограничение отличается от действительно применённого;
невалидное мнение не маркируется принятым. По клику — сообщения и доказательства.

Если итог `confirmed_legacy`, писать «Подтвердили исходный выбор», не придумывать улучшение или veto.
Изменение плана утверждать только при наличии исходного и финального выбора в трассе. Одних разных
decision_id недостаточно. При отказе по данным: «Агенты не запускались: нет пригодного источника».
При сбое LLM показывать фактически выполненную часть и результат восстановления, без общего
обещания «вернулись к исходному плану»: подтверждённые ограничения могли сохраниться.

Приёмка: эксперт без открытия JSON понимает взаимодействие ролей и влияние либо отсутствие влияния
на итог. Число сообщений и токенов — только технические детали.

### F05 · P1 · Объяснить, почему вариант предпочтителен

Компактная таблица: выбранный план и до двух фактически доступных альтернатив. Колонки: действие,
выпуск за указанный горизонт, стоимостной прокси, прокси-тяжесть, причина выбора/отклонения.
Источники: `decision`, `explanation.alternatives`, `explanation.comparison_rule` и подтверждающая трасса.
Правило ранжирования брать из текущего результата: в сценарии может действовать окно стоимости
ради меньшей тяжести, поэтому не зашивать универсальное «самый дешёвый».

«Без действия» показывать только если есть данные именно плана hold на сопоставимых условиях.
`lookahead.initial` не всегда является hold. Не вычитать показатели разных горизонтов и не
рисовать отсутствующие траектории. Если парного сравнения нет — показывать метрики выбранного плана
и честно обозначать отсутствие сравнения. Не показывать деньги в рублях без реальных стоимостей.

Приёмка: каждое число связано с полем результата, единицей и горизонтом; причина предпочтения
согласуется с политикой backend. При отказе до поиска таблица заменена объяснением, а не нулями.

### F06 · P1 · Доказательства за один клик

Три раскрываемых раздела: «Данные», «Прогноз и ограничения», «Трасса решения».
Данные: время среза, значение/возраст/пригодность ЛИМС и ПАК, выбранный источник, происхождение
значений (измерение, оценка, сценарное допущение), причины непригодности.
Ограничения: сера ≤10 мг/кг, остальные применимые проверки, значение/предел/единица/время;
агрегировать повторные временные проверки с худшим запасом, не выдавать 129 проверок за 129 нормативов.
Отдельно стресс-проверки с поимёнными исходами; «5 из 6» не вероятность безопасности.
График строить только по существующему `forecast.points`, с названием объекта прогноза и единицами.
Прогноз потока после ГО не переименовывать в качество товарной смеси; не дорисовывать интервалы.
`forecast_used` учитывать: наличие графика само по себе не доказывает участие прогноза в решении.
Методику временной валидации брать из `forecast-evidence.md`, отдельно от результата текущего прогона.

Приёмка: эксперт может за один клик проверить каждое ключевое утверждение первого экрана.
Отсутствующие данные отображаются как «нет оценки», а не как ноль или прошедшая проверка.

### F07 · P0 · Различать реальную LLM, офлайн-агентов и запись

В видимой строке режима: «Офлайн-агенты», «Внешняя LLM: провайдер/модель» или «Запись прогона».
Живой backend-запуск со scripted provider не называть живой LLM. Replay использует `replaying`
и `run.live`; он не должен снова выглядеть как запрос к серверу. Данные провайдера из payload
показывать как фактический режим результата; до запуска при отсутствии серверных метаданных —
«Режим уточняется при запуске», без выдуманного переключателя провайдера.
Добавить понятное ожидание внешней LLM с текущей ролью и временем; без фиктивного процента готовности.
Показ сохранённой исторической трассы требует явного пути загрузки, если его ещё нет: локальный
replay последнего запуска не считать импортом записи. Такой импорт — отдельная задача при необходимости.

Приёмка: live/offline/replay/fallback визуально различимы. Остановка в браузере не обещает прекращение
запроса на сервере, пока серверная отмена не подтверждена контрактом.

### F08 · P0 · Приёмка перед демонстрацией и остановка изменений

Выполнять после F01–F07. Проверить из сдаваемой сборки: норма, риск качества, плохие данные;
дополнительно транспортную ошибку, остановку, replay и fallback. Для основной тройки использовать
реальные ответы backend. Для редких состояний допустимы явно тестовые фикстуры вне демонстрационного UI.
Норма должна подтверждать отсутствие лишнего действия; если текущий пресет этого не даёт,
подобрать проверенный период и зафиксировать его, не менять правила решения ради демонстрации.

Сценарий показа на 3 минуты: 0:00–0:25 норма; 0:25–1:25 риск/действие/компромисс;
1:25–2:05 вклад агентов; 2:05–2:40 отказ и недостающие данные; 2:40–3:00 ограничения прототипа.
Если внешний провайдер не укладывается — использовать явно обозначенную запись агентного прогона.
Фактический хронометраж обязателен; это целевой бюджет, не уже достигнутый результат.

Проверки: `npm run build`, целевые проверки адаптера статусов и конкурирующих запросов,
ручной браузерный проход основной тройки, отсутствие ошибок консоли и устаревших данных.
После успешной репетиции — только дефекты запуска, достоверности и читаемости.

## Порядок передачи разработчику

F01 → F02 → F03 → F04 → F07 → F05 → F06 → F08.
Первый принимаемый срез: F01–F04 + F07 — работающий, ясный экран с видимыми агентами.
Второй срез: F05–F06 — проверяемое объяснение выбора. Затем конечная репетиция.
Не расширять backend-логику выбора в рамках этих задач. Если для утверждения нет структурного поля,
зафиксировать точечный пробел контракта; не восстанавливать числовые доказательства из свободного текста.
