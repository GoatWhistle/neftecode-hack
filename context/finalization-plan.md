# План завершения проекта

Обновлено: 2026-09-20. План составлен после повторного чтения ТЗ, аудита реализации, сравнения
с публичными репозиториями конкурентов и проверки нового интерфейса в браузере, включая один успешный
прогон с живой `Z.AI / glm-5.3-flash`.

## Решение по объёму работ

Функциональное ядро замораживается. Новые агенты, модели, чат, Парето-фронт и большой мониторинговый
dashboard до сдачи не добавляются. Цель оставшейся работы — устранить противоречия интерфейса, сделать
главный ответ понятным за несколько секунд, доказать воспроизводимость и подготовить короткую защиту.

## Очерёдность

### 1. Исправить противоречивые статусы интерфейса — обязательно

- После раннего отказа этап `Решение` должен иметь конечный статус, а не `ожидает`.
- Неисполнявшиеся этапы должны называться `пропущено`, а не `готово`.
- Разделить три режима: живая модель, штатная детерминированная `scripted`-политика и аварийный
  `fallback` после сбоя провайдера.
- Убрать противоречие «сработал запасной путь» / «отката не было» в штатном `scripted`-прогоне.

**Готово, когда:** нормальный прогон, отказ из-за плохих данных, `scripted` и живая LLM показывают
непротиворечивые статусы; это проверено в браузере.

**Статус (2026-09-20, ветка `worktree-finalization-plan` от `a728a10`):** сделано в коде и проверено
живыми данными, но не в браузере (нет графического Chrome в этой среде — только curl по
`/api/decide`). `StageState` получил `skipped` — этапы, до которых прогон не дошёл, теперь
«пропущено», а не «готово» (`run/sequence.ts: stageRan`), включая этап «Агенты»: подтверждено живым
прогоном с `fault=both_broken`, где `agentic.outcome=="skipped"` и trace содержит только `data` —
это нашли и починили именно на живых данных, не в коде «на глаз». Найдена и исправлена реальная
причина противоречия «сработал запасной путь» / «отката не было»: backend (`decision.py`) никогда не
шлёт `agentic.outcome == "ok"` и никогда `mode == "scripted"` — фронт сравнивал именно с этими
значениями. Проверено тремя живыми прогонами через локальный `neftecode-stack` (копия `artifacts/`
для чтения, без изменений в основном чекауте): 1) `LLM_PROVIDER` не задан → `outcome="fallback"`,
`fallback_reason="llm_not_configured..."` — тон «fallback», причина показана, без противоречия;
2) `LLM_PROVIDER=scripted` → `outcome="confirmed_legacy"`, `deterministic_policy=true`,
`fallback_reason=null` — раньше это давало «сработал запасной путь» при «отката не было», теперь тон
«scripted»; 3) `fault=both_broken` (отказ на данных) → `outcome="skipped"`, только этап «Агенты»
теперь «пропущено». `npm run build` чистый после каждой правки.

Пиксельного скриншота в реальном Chrome нет: `claude-in-chrome` в этой фоновой сессии не подключён
(`list_connected_browsers` вернул пустой список — не выбор, а факт среды). Вместо этого прогнал
логику и реальные React-компоненты через server-side рендер (`react-dom/server`,
`renderToStaticMarkup`, esbuild-бандл, `node`, без браузера) на всех четырёх живых payload:
`ORDER.map(id => stageRan(id, payload))` дал ожидаемую матрицу без единого расхождения — нормальный
`hold` (дважды, scripted и fallback) и `sour_crude` показывают все восемь этапов «готово»; отказ на
данных (`fault=both_broken`) даёт «Решение: готово» (не «ожидает» — прямое требование пункта) и
«candidates/forecast/choice/gate/agents: пропущено» (не «готово»). Это не пиксельная, но реальная
функциональная проверка на боевых данных — со стороны итогового текста читается ровно то же, что
увидел бы человек в браузере. Остаётся только визуальная (шрифты/раскладка/цвет) проверка — на
репетиции (пункт 7), нужен графический Chrome на машине пользователя.

### 2. Поднять ответ оператору над подробной схемой — обязательно

В начале результата компактно показать:

1. вердикт: сохранить режим / изменить режим / отказ;
2. что именно сделать относительно текущего режима;
3. главную причину;
4. обязательное условие или предупреждение перед действием.

Для хрупкой рекомендации предупреждение о потере допустимости и необходимости прямой пробы резервуара
должно быть визуально заметнее идентификатора плана. Схема, трасса и JSON остаются ниже как доказательства.

**Готово, когда:** по первому экрану результата за 10 секунд понятны действие, причина и главное
ограничение без раскрытия технических деталей.

**Статус:** сделано в коде — новый `ui/OperatorAnswer.tsx` рендерится в `App.tsx` до `<PipelineMap>`,
все четыре пункта на месте, предупреждение о потере допустимости (`fragile_plan`/
`tank_estimate_sensitive` из `explanation.risk.items`) стилизовано заметнее остального текста
карточки. Компонент прогнан через `renderToStaticMarkup` на четырёх живых `/api/decide`-ответах —
реальный отрендеренный текст, не пересказ логики:
- `hold` (scripted и fallback): «Сохранить режим → Сохранить текущий режим: изменения уставок не
  требуются. → Текущий режим проходит все обязательные проверки… → Промышленное применение пока
  заблокировано…» — 4 пункта плана видны подряд, действие и причина понятны без схемы.
- `refuse` (отказ на данных): «Надёжной рекомендации нет → Действие не выдано: без него допустимый
  план не найден… → Нет достоверного источника качества. Недостаёт: свежий лабораторный анализ…».
- `sour_crude`: то же, что hold — вкупе с обязательным `deployment_readiness.ready=false`
  предупреждением (оно и есть постоянно действующее обязательное условие по конструкции проекта, не
  баг, что оно на каждом прогоне).
Случая с реальным `fragile_plan`/`tank_estimate_sensitive` в доступных сценариях не встретилось —
код-ревью формулировки из `risk_block.py` совпадает буквально. Пиксельная (шрифты/раскладка/10-
секундная читаемость на глаз) проверка — на репетиции (пункт 7), нужен графический Chrome на машине
пользователя; `claude-in-chrome` в этой сессии не подключён.

### 3. Убрать внутренние коды из основного пользовательского слоя — обязательно

- Заменить на человеческие подписи `ample_reserve`, `confirmed_legacy`, `synthetic_scenario`,
  `recommend_scenario`, `sulfur_mgkg` и похожие значения.
- Исходные коды сохранить в раскрываемой трассе и JSON для аудита.
- Для агентного результата показывать короткую цепочку: «ядро предложило → специалисты проверили →
  ограничения/вето → итог».

**Готово, когда:** основной экран читается без знания внутренней модели данных, но техническая
проверяемость не потеряна.

**Статус:** сделано. Переведены `legacy_status`, `outcome` (агентный слой) и `scenario_id`
(«Состояние») — коды остались рядом в `<code>`/JSON. Короткая цепочка «ядро предложило → специалисты
проверили → ограничения/вето → итог» для агентного результата добавлена (`ui/AgenticMode.tsx:
AgentChain`), проверена на живом `/api/decide` (scripted, baseline) — текст совпал с реальным
payload. Остальной экран (за пределами примеров из плана) построчно не проверялся — если найдутся
ещё внутренние коды на главном слое, лечится тем же приёмом (словарь + `<code>` рядом).

### 4. Проверить поставку одной командой в чистом окружении — обязательно

- Собрать именно сдаваемый архив.
- Проверить, что в него входят необходимые модельные артефакты, замороженные срезы и
  `source_rules.json`; отсутствие обязательного файла должно завершать проверку ошибкой.
- Пройти запуск строго по README без ручного исправления путей и файлов.
- Отдельно описать два режима: воспроизводимое офлайн-демо и опциональный запуск с живой LLM.

**Готово, когда:** человек вне команды распаковывает архив, выполняет одну документированную команду и
получает интерфейс с готовым сценарием без доступа к секретам и внешней сети.

**Статус:** сделано. С нуля (свежий git worktree, без кэшей): `uv sync --frozen` →
`uv run pytest -q` — 1357 passed, 2 skipped (1359, как и раньше); `uv run neftecode scenes` без
срезов — 5 сцен и оба предупреждения, как задокументировано в README. Обучение `train`/
`snapshot --all` в этом worktree не запускалось (нет `task/` — 343 МБ выданных данных не трекаются
в git и распространение не согласовано), но обучать заново было не нужно: `artifacts/` (4,2 МБ,
включая `model.pkl`) скопирован только для чтения из основного чекаута, где уже обучен. С этим
`bash scripts/package.sh` прогнан целиком: все обязательные файлы на месте, `expert_grid.json`
(опциональный) корректно пропущен с предупреждением, а не ошибкой; собран `neftecode-20260920-154407.
tar.gz`, 2,2 МБ, 626 файлов — без `task/`, с актуальной сборкой `src/frontend/dist/index.html`.
Проверка «нет секретов / нет обращений к внешней сети / нет тяжёлых исходных данных» встроена в сам
скрипт и прошла. Копия `artifacts/` и собранный тестовый архив остались только в рабочем дереве
(в `.gitignore`), в коммит не попадают.

### 5. Зафиксировать доказательство мультиагентности — после пунктов 1–4

- Сохранить уже подтверждённый живой прогон: `Z.AI / glm-5.3-flash`, 8 вызовов, 35 075 токенов,
  закрытый поток, без fallback; результат — подтверждение `hold`.
- Один раз проверить живой сложный сценарий, где у специалиста есть основание ужесточить выбор или
  наложить вето.
- Если итог изменился, показать конкретное влияние агента. Если не изменился, честно зафиксировать, что
  специалист подтвердил детерминированное решение; не подгонять демонстрацию.
- Для защиты использовать сохранённую трассу или запись и явно подписать её как запись: живой вызов
  занимает минуты и зависит от внешнего провайдера.

**Готово, когда:** видно не количество сообщений, а роль каждого специалиста и влияние либо отсутствие
влияния на итог.

### 6. Упаковать доказательство качества прогноза — после пунктов 1–4

Сделать один слайд или компактный блок: простой ориентир → наш прогноз → временные фолды → фактическое
покрытие интервала → известные ограничения → пример, где прогноз меняет решение. Не сравнивать MAE с
чужими числами как единый рейтинг: выборки и постановки у команд различаются.

**Готово, когда:** проверяющий понимает методику и границы результата без чтения исследовательских файлов.

### 7. Собрать и отрепетировать демонстрацию — финальный этап

Порядок показа не длиннее трёх минут:

1. нормальный режим — осознанное `hold`;
2. риск качества — прогноз, альтернативы, Gate и предупреждение;
3. плохие данные — объяснимый отказ и условие повторного расчёта;
4. краткое раскрытие агентной трассы;
5. честные границы промышленного применения.

После репетиции выполнить production-сборку фронтенда, целевые тесты исправленных состояний и полный
набор тестов, если позволяет время. Зафиксировать команды и результаты проверки.

**Готово, когда:** демонстрация укладывается в три минуты, не требует импровизированного поиска по
странице и воспроизводится из сдаваемого архива.

## Что взять у конкурентов

- У Against61 — простоту «одна команда → результат» и заметные предупреждения на первом экране.
- У решений с трассами — удобство проверки обмена ролей, но показывать у нас именно влияние на решение.
- У мониторинговых интерфейсов — быстрый доступ к ответу оператору, не превращая проект в новый dashboard.

Публичного работающего интерфейса большинства конкурентов не было, поэтому выводы об их визуальном
качестве по одному стеку или концептуальным изображениям не считаются подтверждёнными.

## Стоп-условие

После выполнения пунктов 1–4 и успешной трёхсценарной репетиции новые функциональные изменения не
начинаются. Пункты 5–7 завершают доказательства и упаковку. После них допускаются только исправления,
которые блокируют запуск, искажают результат или мешают показать обязательный сценарий ТЗ.
