# План завершения проекта

Обновлено: 2026-09-20. План составлен после повторного чтения ТЗ, аудита реализации, сравнения
с публичными репозиториями конкурентов и проверки нового интерфейса в браузере, включая один успешный
прогон с живой `Z.AI / glm-5.3-flash`.

## Решение по объёму работ

Функциональное ядро замораживается. Новые агенты, модели, чат, Парето-фронт и большой мониторинговый
dashboard до сдачи не добавляются. Цель оставшейся работы — устранить противоречия интерфейса, сделать
главный ответ понятным за несколько секунд, доказать воспроизводимость и подготовить короткую защиту.

## Очерёдность

### 1. Исправить противоречивые статусы интерфейса — обязательно

- После раннего отказа этап `Решение` должен иметь конечный статус, а не `ожидает`.
- Неисполнявшиеся этапы должны называться `пропущено`, а не `готово`.
- Разделить три режима: живая модель, штатная детерминированная `scripted`-политика и аварийный
  `fallback` после сбоя провайдера.
- Убрать противоречие «сработал запасной путь» / «отката не было» в штатном `scripted`-прогоне.

**Готово, когда:** нормальный прогон, отказ из-за плохих данных, `scripted` и живая LLM показывают
непротиворечивые статусы; это проверено в браузере.

**Статус (2026-09-20, ветка `worktree-finalization-plan` от `a728a10`) — ЗАКРЫТО, проверено пиксельно
в реальном Chrome.** `StageState` получил `skipped` — этапы, до которых прогон не дошёл, теперь
«пропущено», а не «готово» (`run/sequence.ts: stageRan`), включая этап «Агенты»: подтверждено живым
прогоном с `fault=both_broken`, где `agentic.outcome=="skipped"` и trace содержит только `data` — это
нашли и починили именно на живых данных, не в коде «на глаз». Найдена и исправлена реальная причина
противоречия «сработал запасной путь» / «отката не было»: backend (`decision.py`) никогда не шлёт
`agentic.outcome == "ok"` и никогда `mode == "scripted"` — фронт сравнивал именно с этими значениями.

Сначала прогнал логику через SSR (`renderToStaticMarkup` без браузера) — `claude-in-chrome` в сессии
тогда не был подключён (`list_connected_browsers` пуст). Затем расширение подключилось (пользователь
открыл Chrome), и все три сценария пройдены **вживую, с реальным кликом и скриншотом**, живая модель
`zai/glm-5.3-flash` (ключ из `.env`, переменная `token`, с явного разрешения пользователя),
через `uv run neftecode serve`:
1. **`ample_reserve`, все источники исправны** — «Решение принято с участием живой модели», все 8
   этапов «готово», «Причина отката: отката не было» — никакого «сработал запасной путь».
2. **`sour_crude`** (сложный сценарий, см. пункт 5) — то же самое: живая модель, все этапы «готово»,
   цепочка агентов отрендерилась с реальным текстом от Z.AI.
3. **`fault`: лаборатория и анализатор недоступны (`both_broken`)** — «08 Решение: ГОТОВО» (не
   «ожидает» — прямое требование пункта), «03 Кандидаты» и **«07 Агенты: ПРОПУЩЕНО»** (курсивом,
   приглушённым цветом — не «готово»); поле у «Агенты» подписано «Почему агенты не привлекались:
   `data_refusal`», а не «Причина отката» — ровно то текстовое исправление, которое до этого было
   предсказано SSR-рендером, теперь видно на реальном экране.

Побочная находка при первой попытке: `neftecode-stack` (4-процессный gateway) не реализует
`/api/stream`, только `/api/decide` — фронтенд получал 404 и красиво показывал «сервер ответил 404»
(это тоже honest failure, не крах). Правильный процесс для браузерной демонстрации — **`uv run
neftecode serve`** (однопроцессный сервер с `presentation/web/server.py`, где `/api/stream` есть).
Стоит явно отметить в README, какой из двух серверов для чего: `neftecode-stack` — для HTTP-контрактов
между процессами, `neftecode serve` — для интерфейса браузера.

### 2. Поднять ответ оператору над подробной схемой — обязательно

В начале результата компактно показать:

1. вердикт: сохранить режим / изменить режим / отказ;
2. что именно сделать относительно текущего режима;
3. главную причину;
4. обязательное условие или предупреждение перед действием.

Для хрупкой рекомендации предупреждение о потере допустимости и необходимости прямой пробы резервуара
должно быть визуально заметнее идентификатора плана. Схема, трасса и JSON остаются ниже как доказательства.

**Готово, когда:** по первому экрану результата за 10 секунд понятны действие, причина и главное
ограничение без раскрытия технических деталей.

**Статус — ЗАКРЫТО, проверено пиксельно.** `ui/OperatorAnswer.tsx` рендерится в `App.tsx` до
`<PipelineMap>`, все четыре пункта на месте, предупреждение о потере допустимости стилизовано
заметнее остального текста карточки. Живьём в Chrome (`uv run neftecode serve`, три сценария) экран
читается ровно так, как задумано: **«Сохранить режим» крупным заголовком → «Сохранить текущий режим:
изменения уставок не требуются.» → причина одной строкой → рамка с предупреждением о промышленном
применении** — всё это видно на первом экране без скролла и без единого технического термина; то же
самое для отказа — **«Надёжной рекомендации нет» (подчёркнуто, красным) → «Действие не выдано…» →
причина → предупреждение**. Случая с реальным `fragile_plan`/`tank_estimate_sensitive` в доступных
сценариях не встретилось — код-ревью формулировки из `risk_block.py` совпадает буквально, критическая
стилизация (`.answer__note--critical`) кодом проверена, но живого триггера не было.

### 7. Собрать и отрепетировать демонстрацию — финальный этап

Порядок показа не длиннее трёх минут:

1. нормальный режим — осознанное `hold`;
2. риск качества — прогноз, альтернативы, Gate и предупреждение;
3. плохие данные — объяснимый отказ и условие повторного расчёта;
4. краткое раскрытие агентной трассы;
5. честные границы промышленного применения.

После репетиции выполнить production-сборку фронтенда, целевые тесты исправленных состояний и полный
набор тестов, если позволяет время. Зафиксировать команды и результаты проверки.

**Готово, когда:** демонстрация укладывается в три минуты, не требует импровизированного поиска по
странице и воспроизводится из сдаваемого архива.

**Статус — не начат, но есть заготовка по реальным замерам этой сессии.** В браузере вживую пройдены
сцены 1 (нормальный `hold`, `ample_reserve`) и 3 (плохие данные, отказ на `both_broken`) — обе за
секунды; сцена сложного агентного сценария (`sour_crude`, ближе к «риску качества» пункта 2, хотя не
из snapshot 24.07.2026) заняла **≈3 мин 03 с** живого вызова Z.AI целиком, из них этап «Агенты» —
основная часть времени (несколько ходов оркестратора + консультация обоих специалистов). Это значит:
**полные три сцены с живой моделью в кадре физически не укладываются в три минуты** — заявленный
бюджет реалистичен только если сцена 2 показывается по заранее сохранённой трассе/записи (как и
предписывает пункт 5: «живой вызов занимает минуты… для защиты использовать сохранённую трассу»), а
не вызывается заново на публике. Сцену «риск качества, прогноз, альтернативы» на настоящем snapshot
24.07.2026 в эту сессию не прогонял — нужно отдельно. Само хронометрированное прочтение вслух и решение,
что показывать живьём, а что по записи — шаг пользователя.

- У Against61 — простоту «одна команда → результат» и заметные предупреждения на первом экране.
- У решений с трассами — удобство проверки обмена ролей, но показывать у нас именно влияние на решение.
- У мониторинговых интерфейсов — быстрый доступ к ответу оператору, не превращая проект в новый dashboard.

Публичного работающего интерфейса большинства конкурентов не было, поэтому выводы об их визуальном
качестве по одному стеку или концептуальным изображениям не считаются подтверждёнными.
