## A1 — P1: влияние режима на T95 потеряно между процессом и смесью

Место: `src/neftecode/planner.py:190–212`, `src/neftecode/process.py:254`. Задачи: T12, T15, T25.

`ProcessChain` вычисляет изменившийся `stream.t95_c`, но Planner его не передаёт в Blender/проверку. Корректируется только сера, а T95 берётся из постоянных свойств резервуаров. Это делает итоговую оценку T95 нечувствительной к действию АВТ/ГО даже при наличии собственной модели такого влияния.

Контрпример на baseline: температура выхода печи АВТ 372 → 400 °C; рецепт main 90%, reserve 10%; выпуск 100 т/ч. Собственная цепочка после 0.5 ч даёт T95=380.2 °C. По объявленному в проекте линейному правилу смеси при таком основном компоненте получилось бы 376.58 °C, выше сценарного предела 360. Но gate постоянно проверяет 351.2 и возвращает feasible=True. Сера при этом 9.817697 мг/кг и не блокирует план.

Это контрпример согласованности программных моделей, не утверждение о фактической T95 завода. Если компонент хранится в резервуаре, вместо прямой подстановки нужна согласованная модель обновления свойств запаса; текущая независимость T95 от меняющегося притока этим не обоснована.

```python
from neftecode.scenario import load_scenario
from neftecode.planner import Planner, PlanCandidate, PlanStepSpec
p = Planner(load_scenario('config/scenarios/baseline.json'))
c = p.base_controls()
c['avt_furnace_outlet_temp_c'] = 400
plan = PlanCandidate('repro', (PlanStepSpec(0, c, {'main': .9, 'reserve': .1}, 100),), changes=1)
e = p.evaluate(plan)
stream = p.chain.run_at(.5, ((0, {'avt_furnace_outlet_temp_c': 400}),))
print(stream.t95_c)  # 380.2
print(max(x.observed for x in e.gate.checks if x.constraint_id == 'quality.t95_c'))  # 351.2
print(e.feasible)  # True
```

Исправление считается готовым, когда воздействие доходит до всех затрагиваемых свойств смеси через одну согласованную модель потока/резервуара, а контрпример не проходит на старом статическом T95.

## A2 — P1: повторное решение не видит текущих запасов и времени

Место: `src/neftecode/replay.py:68–70,115–117,130–154`; `src/neftecode/planner.py:171`. Задачи: T21, T25; затем перепроверить T17/T22.

`Replay.step()` передаёт в оркестратор только confirmed_controls. Остатки `execution.tanks` и `clock_hours` не передаются; Planner вновь создаёт InventoryLedger из начального сценария. Все подтверждённые действия переводятся в время 0.0 независимо от confirmed_at и прошедшего времени. `run()` не вызывает draw/advance; `_apply()` лишь добавляет подтверждение.

Воспроизведено: у sour_crude запас reserve изменён с 50 до 1 т, часы продвинуты на 2. Решение имеет тот же decision_id и рекомендует прежнюю долю reserve 20%. Сохранить объект состояния в JSON недостаточно: он должен влиять на следующий расчёт.

```python
from neftecode.scenario import load_scenario
from neftecode.replay import Replay, ExecutionState, SIMULATED
s = load_scenario('config/scenarios/sour_crude.json')
r = Replay(s, budget=400)
a = ExecutionState.from_scenario(s)
b = a.draw({'reserve': 49}).advance(2)
first = r.step(SIMULATED, execution=a)['decision']
next_ = r.step(SIMULATED, execution=b)['decision']
print(b.tanks['reserve'].inventory_t, b.clock_hours)  # 1.0, 2.0
print(first['decision_id'] == next_['decision_id'])  # True
```

Нужна сквозная проверка нескольких решений с выполненными действиями, фактическим расходом/притоком и относительным временем оставшегося отклика. Пауза/продолжение должны сохранять поведение этого цикла, а не только сериализацию.

## A3 — P2: запреты агентов не управляют выбором; повторный поиск не может найти новый вариант

Место: `src/neftecode/orchestrator.py:111–150,169–177,226–243`. Задача: T18, повторная проверка T25.

Два проявления одной незавершённой интеграции:

1. Ответы quality/reliability.review используются в журнале. Допустимость и выдача определяются evaluation.feasible, а не verdict агентов. Введённый через штатное поле quality агент с `verdict='fail'` и явным veto всё равно получил итог hold и выбранный план; в финальном trace одновременно записан fail. Собственный общий gate этим не обходится, но обещанное право агента запретить решение отсутствует.
2. Каждый раунд вызывает тот же build_plans(budget) с тем же сценарием. После полного первого перебора повторный раунд только удаляет часть уже проверенных вариантов. Если допустимого варианта сначала не было, он не появится от такого фильтра. Запреты quality/control/model добавляются в журнал, но `_forbidden` их даже не применяет. Показ уменьшения количества кандидатов не доказывает содержательное согласование действий.

Проверка первого проявления:

```python
from neftecode.orchestrator import Orchestrator
from neftecode.scenario import load_scenario
class VetoQuality:
    def review(self, evaluation):
        return {'agent': 'quality', 'checked': 1, 'passed': 0,
                'vetoes': ['контрольный запрет'], 'unknown': [], 'verdict': 'fail'}
d = Orchestrator(load_scenario('config/scenarios/baseline.json'),
                 quality=VetoQuality()).decide(budget=80)
print(d['status'])  # hold; trace quality содержит fail
```

Исправление: определиться с реальными полномочиями ролей и сделать обязательные ответы частью решения. Если сохраняется veto/replan, новые предложения должны зависеть от причины запрета и иметь возможность дать новый допустимый вариант. Нужен тест «первый набор запрещён → другой план найден», а не только «второй набор меньше».

## A4 — P2: единый gate принимает отсутствующие обязательные поля

Место: `src/neftecode/gate.py:71–79,126–130,187–207`. Задачи: T15, T25.

Отсутствующий управляющий параметр пропускается через continue; запасы проверяются только по переданным ключам; terminal=None означает отсутствие проверки конечного резерва, даже если правило задано сценарием.

Подтверждён прямой вызов публичной проверки с сеткой 0…3 ч, нормальными значениями трёх свойств, controls={}, inventories={}, recipe={'main':1}, throughput=100 и без terminal: feasible=True, причин отказа нет. Внутренний Planner обычно заполняет эти поля, поэтому это дефект границы единой проверки, а не доказательство такого обхода штатным UI.

```python
from neftecode.scenario import load_scenario
from neftecode.planner import Planner
from neftecode.gate import TrajectoryStep, check_plan
s = load_scenario('config/scenarios/baseline.json')
steps = [TrajectoryStep(t, {'sulfur_mgkg': 8, 't95_c': 350, 'cetane_number': 52},
                        {}, {}, {'main': 1}, 100) for t in Planner(s).grid()]
print(check_plan('empty', steps, s).feasible)  # True
```

Исправление: определить обязательный состав входа по сценарию; отсутствующее critical-поле и результат требуемой конечной проверки должны давать unknown/отказ. Проверить начало/конец и полноту временной сетки отдельно.

## A5 — P2: экран скрывает рецепт одношаговой рекомендации

Место: `src/neftecode/ui.py:75–78,92–99`. Задачи: T23, T24/T25 для повторной проверки.

Блок «Что делать» выводит только controls, выпуск и дозу. Рецепт выводится исключительно в блоке плана при steps.length > 1.

Подтверждено в браузере: baseline → reserve недоступен → Пересчитать. Решение recommend_scenario требует заменить main 90%/reserve 10% на main 100%; все уставки и выпуск остались прежними. На экране видны только неизменившиеся числа, состава 100% main нет. Значит оператор не может понять единственное нужное действие. Сведения не спасает журнал: он показывает trace/gate, а не удобную полную инструкцию выбранного рецепта.

Исправление: всегда показывать ближайший рецепт и изменение относительно текущего, в том числе для одного шага. Для будущих шагов также показывать управляющие изменения и дозу, а не только состав/выпуск. Проверять видимый DOM, а не наличие данных во встроенном JSON.

## A6 — P2: оценка риска T95 использует порог серы 10

Место: `src/neftecode/cli.py:86`, `src/neftecode/forecast.py:17–27,131–137`. Задача: T08; отчёты T27 перепроверить после исправления.

Обучение T95 вызывает run_experiment(target='actual_target', limit=None); функция подставляет cfg['sulfur_limit']=10. Кроме того, метрика «около предела» жёстко использует диапазон 5–15. Для температуры в градусах это неверные критерии.

В сохранённом artifacts/metrics.json → extra_targets.t95_c.models.last_lab.test: predicted=199, actual_exceedances=199, recall=1.0, mae_near_limit=None. Такая полнота обнаружения не характеризует реальный риск T95. Обычная MAE сама по себе этой ошибкой не опровергается, и выбор модели делается по MAE; ошибка именно в предметных метриках/отчёте.

Исправление: предел/направление/окрестность задаются для конкретного свойства; без согласованного предела метрики превышений не вычисляются. Не переносить серные значения в другой показатель.
