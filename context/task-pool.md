## Почему дефекты не были видны

1. «Готово» определялось через показ (экран за 10 с, демо за 3 мин), а не через корректность;
   «закрыто» означало закрытие наблюдавшегося дефекта (бывший `finalization-plan.md`).
2. Замороженные эталоны и тест независимой оценки проверяют согласованность с прошлым выводом,
   включая неверный. Тест исследования сравнивает с JSON при budget=400 и остаётся зелёным.
3. Дефекты сидят на стыках дублированных путей (demo ≠ live, gateway ≠ serve), а тестов
   сравнения путей нет. Тест gateway проверяет `/api/decide`, хотя фронт с 19.09 на `/api/stream`.
4. Тесты повторяют допущения кода: нет отрицательных случаев вроде «T6 есть, F9 нет».
5. У фронта нет автотестов; подписи и статусы проверялись глазами.
6. Известные проблемы записывались как «оговорки» (стек в бывшем `finalization-plan.md`).
7. Артефакты исследований не привязаны к конфигурации — вывод устарел молча после смены бюджета.
8. Модель резервуара заморожена до ответа организаторов; ответ 21.09 её устарил.
9. Аудиты сверяли код со своим планом, а не с ТЗ.

## Ответ организаторов 21.09 (резервуар)

«Объём резервуара принять 5 000 м³. Оборачиваемость считать исходя из предположений, что
паспортизация занимает половину суток, слив резервуара сутки.»

Следствия (выведено, не выдано): при ρ = 836.3 кг/м³ вместимость ≈ 4180 т. При притоке
212.6 т/ч налив ≈ 19.7 ч. Цикл = налив + 12 ч паспорт + 24 ч слив ≈ 55.7 ч. Парк из N
резервуаров замыкается при q ≤ (N − 1)·C/36: N = 3 — до 232.3 т/ч, N = 4 — до 348.5 т/ч. Приток
`ht.F26`·ρ выше 232.3 т/ч 25.6% времени (максимум 278.6), поэтому принято N = 4 (решение 21.09,
см. `agent-prompt.md`). Слив за сутки ≈ 174.2 т/ч. В смешение идёт паспортизованная партия с
известным качеством, режим ГО влияет только на наливаемую. Текущая модель — один
непрерывно перемешиваемый объём парка (`main`, 4000 т, вместимость не задана), без партий.

```
domain/                               без изменений, кроме резервуаров (этап 4)
application/
  conditions/                         правки сценария, инъекции отказов, canonical/defaults
  ports/scenarios.py                  ScenarioRepository, SnapshotRepository
  ports/decisions.py                  DecisionRunner (в процессе или по HTTP)
  ports/progress.py                   ProgressSink + отмена
  services/robustness.py              из evaluation
  services/tank_estimate.py           из evaluation
  use_cases/advise_under_conditions.py  единый use case, возвращает DTO
  use_cases/decision/reviews.py       QualityReview / ReliabilityReview
infrastructure/
  scenarios/file.py, scenarios/http.py
  remote/decision_client.py
presentation/web/
  api.py                              единственный набор маршрутов
  presenter.py                        DTO → payload экрана, подписи
  query.py                            разбор query-строки
composition/                          только сборка
services/                             только точки входа процессов
evaluation/                           только offline
```

Нарушения, которые это устраняет: A — use case размазан по composition/presentation/services;
B — правка сценария в presentation; C — два HTTP API; D — runtime-код в evaluation;
E — файловый I/O в presentation; F — коллизия имён агентов; G — прогресс через `threading.local`;
H — архитектурный тест разрешает `services → presentation, evaluation`.

## Целевое состояние системы

### Как считается ответ

1. **Срез** хранит состояние, доверие и два прогноза (основной и no-PAK); возраст каждого измерения известен.
2. **Сценарий** описывает парк из нескольких резервуаров по 5000 м³ со стадиями налив / паспорт / слив;
   у каждого числа есть `source` и ссылка, неизвестное — `open`, и расчёт, которому оно нужно, отвечает «неизвестно».
3. **Условия** обрабатывает один use case `AdviseUnderConditions` — одинаково для экрана, CLI, Docker и стека.
4. **Привязка:** прогноз выбран по фактическому доверию к источникам; ход T6 разрешён только при измеренных
   T6 и F9 в области отклика; сера наливаемой партии считается из данных с начала налива.
5. **Ядро** моделирует АВТ → ГО → наливаемую партию → прогноз её паспорта → смешение паспортизованных
   партий с резервным компонентом, запрещает переполнение; запас реакции — остаток налива. Далее Gate,
   ранжирование (или Парето, если принят G4), упреждение и проверка устойчивости.
6. **Агенты** в прежних полномочиях; журнал обмена виден в карточке; Stop отменяет вызовы LLM;
   при отключении этап честно «пропущено».
7. **Экран** показывает происхождение каждого числа из payload.

### Что останется ограничениями

- Советчик, а не управление; `commercial_release_allowed = false`, проверены не все свойства товарного топлива.
- Часть параметров сценарная: стоимости, резервный компонент, текущая стадия резервуаров без тега уровня.
- β и модель цепочки оценены по истории; причинный эффект на заводе не доказан.
- Преимущество над простым правилом — таким, каким его покажет независимый оценщик (E2), в том числе нулевым.
- Пункты этапа 6, где принят обоснованный отказ, остаются записанными отказами.
